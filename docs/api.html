REST API

How the API works. For every endpoint, parameter and schema, see the API Reference.

Browse the API Reference →

The REST API is mounted at /api/v1/. Requests and responses are JSON, except where a route takes a multipart upload, returns a file, or returns another format; the reference marks those. Timestamps are RFC 3339 strings. Resource IDs are UUIDs.

Tickets also carry a human-readable tracking number such as GHD-2026-000001. The prefix (GHD) is the ticket_prefix setting, so your instance may use another. Every route under /api/v1/tickets/{id} accepts a tracking number in place of the UUID. See Visibility & tracking numbers.

Base URL

<BASE_URL>/api/v1

Quick example

curl https://helpdesk.example.com/api/v1/tickets \
  -H "Authorization: ApiKey GHD_…"

The key needs the tickets:read scope. Without it the same request returns 403.

Authentication

MethodHow to authenticateBest for
Session cookie POST to /api/v1/auth/local/login. The server sets an HttpOnly ghd_session cookie, and browsers send it on later requests. SAML and OIDC sign-in create the same kind of session. A session that has passed the password but not its second factor (a TOTP code or a passkey) is refused with 403 mfa_required on routes that need one. That session lasts 5 minutes from the password step, or 15 minutes when the user still has to set up a second factor (for a new self-registered account, counted from email verification). After that it is gone and requests are refused with 401. The built-in React SPA
API key Authorization: ApiKey GHD_<64 hex characters>. The GHD_ prefix is part of the token. It is shown once, when the key is created. The key acts at its owner's role, counts as having passed MFA, and is limited to its scopes. Administrators can make keys, and staff can make their own when an administrator allows it (see API keys). A key cannot make keys. Scripts, CLI tools, CI pipelines, monitoring
OAuth2 JWT POST to /api/v1/auth/oauth/token with "grant_type": "client_credentials", client_id and client_secret in a JSON body (form encoding is refused). The token lasts one hour (expires_in: 3600). Send it as Authorization: Bearer <token>. A client acts through its own service user, an account created with the client and named after it, at that user's role (staff or user, never administrator), so it cannot reach admin-only routes. Disabling that user or deleting the client stops its tokens on the next request. See OAuth clients and their service user. Server-to-server integrations (JIRA, chatbots)
Guest token Authorization: Guest <token>, from a link in an email. It names one ticket and grants nothing else. See Guest access. Reporters without an account

The MCP server at /mcp accepts the same session, API key and OAuth2 JWT authentication as the REST API. See MCP Server for connection details.

Scopes

API keys and OAuth clients carry scopes. A session does not need them. A credential acts at its owner's role (for an API key) or at the staff role (for an OAuth client), and its scopes narrow that further. A scope never widens what the role allows.

A scope is resource:read or resource:write, and write implies read on the same resource. The resources are:

  • tickets, users, groups, categories, tags, canned_responses, sla, settings, plugins, webhooks and credentials: read and write.
  • audit: read only. No credential can write the audit log. The admin audit view needs audit:read; tickets:read does not reach it.
  • There is no wildcard. * and tickets:* grant nothing.
  • An empty list denies everything. Creating a key or an OAuth client without scopes answers 400 scopes_required. An unknown scope answers 400 invalid_scope.
  • A credential cannot grant a scope it does not hold itself, which answers 403 insufficient_scope. A request outside the credential's scopes gets the same answer.

The catalogue is served by GET /api/v1/admin/scopes, which needs credentials:read. Credentials issued before scopes were enforced (1.2.0) carry none and stop working until they are reissued. See Upgrading to 1.2.0.

An administrator signed in through the browser lists and deletes every API key, whoever owns it. An API key can list and delete only itself: another key's id, its owner's other keys included, answers 404 not_found. Before 1.3.0 a signed-in administrator saw only their own keys, and a key could delete another administrator's key if it knew the id.

Settings that need a signed-in administrator

An API key or OAuth client cannot change these settings, whatever scopes it holds. The settings endpoint answers 403 session_required. Writes to the SAML and OIDC configuration, a user's own password and MFA enrolment, and the MFA and passkey sign-in routes refuse machine credentials the same way. Repointing an identity provider, switching off MFA or opening registration would each give whoever holds the key a session they should not have.

The settings a machine credential cannot change are:

  • Sign-in: saml_enabled, saml_metadata_url, saml_metadata_xml, saml_cert_pem, saml_key_pem, oidc_enabled, oidc_issuer_url, oidc_client_id, oidc_client_secret, oidc_redirect_url.
  • Second factor: mfa_enabled, mfa_enforced_roles.
  • Accounts: self_signup_enabled, open_registration_enabled, allowed_email_domains.
  • Guests: guest_submission_enabled.
  • API keys: staff_can_create_api_keys and api_key_max_lifetime_years.
  • Who sees and who is handed tickets: ticket_scope_enforced, auto_assign_group_id and auto_assign_user_ids. A key that could switch scope enforcement off, or point auto-assignment at an account it controls, would widen what that account sees or is given.
  • Closed tickets and audit: closed_reopen_policy, audit_mask_requester_names, audit_retention_days, staff_can_view_ticket_change_history.
  • Attachment scanning: attachment_scan_address, attachment_scan_policy, attachment_allowed_types, attachment_infected_handling, attachment_mismatch_handling.
  • Reputation lookups: attachment_reputation_refresh, attachment_reputation_virustotal_enabled, attachment_reputation_virustotal_key, attachment_reputation_metadefender_enabled, attachment_reputation_metadefender_key, attachment_reputation_polyswarm_enabled, attachment_reputation_polyswarm_key, attachment_reputation_circl_enabled.
  • Deprecated, still writable: attachment_vt_lookup, attachment_vt_api_key, attachment_reputation_provider, attachment_reputation_api_key.

API keys

An API key belongs to a person and acts at that person's current role. A key is created by a signed-in person: an administrator, or a staff member for their own key when Staff may create their own API keys is on. Requesters never own keys, and neither do service accounts.

  • Where: GET and POST /api/v1/me/api-keys, GET /api/v1/me/api-keys/scopes and DELETE /api/v1/me/api-keys/{id} for your own keys (session only; a requester gets 403), and GET and POST /api/v1/admin/api-keys for an administrator. POST /api/v1/admin/api-keys takes an optional user_id to issue a key for a staff member or for yourself, from a signed-in administrator only. It refuses another administrator (400 cannot_issue_for_administrator), a requester (400 requester_cannot_own_key) and a service account (400 service_account_cannot_own_key). Responses carry user_id and created_by.
  • A key cannot make keys or OAuth clients. POST /api/v1/admin/api-keys, POST /api/v1/admin/oauth-clients and the /me/api-keys routes answer 403 session_required to an API key and 403 forbidden to an OAuth client. A key can still list and delete clients, and list and revoke itself.
  • A key cannot write users. It can read users and groups. These answer 403 session_required to an API key (403 forbidden to an OAuth client): POST /admin/users, PATCH /admin/users/{id}, DELETE /admin/users/{id}, POST /admin/users/{id}/password, POST and DELETE on /admin/groups/{id}/members…, and POST and DELETE /admin/groups/{id}/scopes. That covers creating, renaming, re-addressing, promoting, disabling and deleting accounts, password and second-factor resets, and group membership and scope. A key that could write a user could make itself a person: set a password, sign in, and create keys that outlive it.
  • Scopes never exceed the owner's role. A staff key can carry tickets:read, tickets:write, groups:read and audit:read (users:read is no longer offered: its one staff route, the requester lookup, is session-only); an administrator's key can carry any scope. Anything else is 400 invalid_scope. GET /api/v1/admin/scopes?role=staff lists what a staff key may carry. users:write is no longer offered and a new key cannot hold it; keys that already hold it keep it, and it opens nothing.
  • Every new key must expire. While the maximum lifetime is a number of years (api_key_max_lifetime_years, 1 to 5, default 2), expires_at is required (400 expires_at_required) and may be no later than that many years from now (400 expires_at_too_far). Only when the setting is Never (-1) may it be omitted. The limit is checked when the key is created, not when it is used. Both key lists carry beyond_limit for a key with no expiry or one past the current limit.
  • GET /api/v1/me gains can_create_api_keys and api_key_max_lifetime_years.
  • Webhooks a key makes stop with the key. A webhook an API key created, or last changed the URL of, is paused once that key is no longer active: revoked, expired (a key counts as expired from the instant of its expiry), or its owner disabled or deleted. A key cannot edit a paused hook (403 webhook_paused). A signed-in administrator re-approves it with POST /api/v1/admin/webhooks/{id}/reapprove (session only).
  • POST /api/v1/admin/users/{id}/password takes revoke_api_keys (default false) to delete every key the account owns. If the keys cannot be revoked after the password was reset, the answer is 500 keys_not_revoked; if the sessions cannot be ended, 500 sessions_not_ended.

Visibility and tracking numbers

A ticket you may not see answers 404 not_found, the same answer as a ticket that does not exist. It is never 403, so tracking numbers, which are sequential, cannot be walked to learn which tickets exist. Earlier releases answered 403; from 1.3.0 the answer is 404.

Every route under /api/v1/tickets/{id} accepts a tracking number in any letter case in place of the UUID, so ghd-2026-000001 and GHD-2026-000001 reach the same ticket. There is no separate lookup endpoint. A value that is not a UUID is looked up as a tracking number, so one that names no ticket answers 404 not_found. Before 1.3.0 only GET /api/v1/tickets/{id} took a tracking number, and the other routes answered 400.

Closed tickets

Closed is read-only and terminal by default. Nothing moves a closed ticket back to an open state unless the closed_reopen_policy setting allows the caller's role. The values are off (the default, nobody may reopen), admin (administrators only) and staff_admin (staff and administrators). A requester can never reopen a closed ticket.

  • A requester's reply, upload, custom-field edit or link on a closed ticket answers 409 ticket_closed. Staff and administrators can still post replies to a closed ticket.
  • A reopen the policy does not allow answers 409 ticket_closed, with a message that says why.
  • POST /api/v1/tickets/{id}/follow-up opens a new ticket linked to a closed one, and answers 201 with the new ticket. Staff and administrators can open one for any closed ticket they can see; a requester can open one for their own, once. A ticket that is not closed answers 409 ticket_not_closed. A requester's second follow-up of the same ticket answers 409 follow_up_exists; staff and administrators are not limited.
  • A requester's reply to a Resolved ticket after the reopen window answers 409 reopen_window_closed.
  • A guest's write to a closed ticket answers 404 not_found. A guest opens a follow-up with POST /api/v1/guest/follow-up.

Attachment downloads

Attachments are download-only. GET /api/v1/tickets/{id}/attachments/{attachId} streams the file with these headers:

Content-Type: application/octet-stream
Content-Disposition: attachment; filename="…"
Vary: Sec-Fetch-Dest
Cache-Control: private, max-age=3600

The content type is always application/octet-stream, whatever the file claims to be. No browser renders that type, so a file opened from the link is saved, not shown. The header check below covers browsers that request a file to display it. It cannot stop a script that fetches the bytes and renders them itself.

The route checks Sec-Fetch-Dest. Only document, empty and an absent header are accepted. A request whose header says the browser will render the response, such as an image or a frame, is refused with 403 not_downloadable. Command-line clients send no such header and are not affected. An <a download> click and a fetch() send empty and are accepted.

Uploads, the attachment object and the reputation fields are described in the API Reference. For why the help desk never renders an attachment, see Attachment Security.

Guest access

Guests reach six routes under /api/v1/guest. None takes a session, an API key or an OAuth token.

  • POST /guest/tickets submits a ticket. The body has subject, description, category_id, guest_email and guest_name (the last two are required), and optionally guest_phone. It answers 201 with the tracking number and nothing else. The access link goes by email.
  • POST /guest/resend asks for a new access link, given a tracking number and an address. It answers 202 whether or not anything matched.
  • GET /guest/ticket, POST /guest/replies, POST /guest/attachments and POST /guest/follow-up take the guest token and act on the one ticket it names. POST /guest/attachments answers the generic 404 unless an administrator has turned on Guests may attach files (off by default); when it is on, GET /api/v1/site reports guest_attachments_enabled and the limits (guest_attachment_max_bytes, guest_attachment_max_per_ticket, guest_attachment_uploads_per_hour). Over a limit the answers are 413 too_large, 409 guest_attachment_limit and 429 rate_limited.

Turning guest_submission_enabled off makes every guest route answer 404: submit and resend, and also the routes that take a token (read, reply, upload and follow-up). The body is the same as for a wrong token, so a client cannot tell the two apart. Links already sent are suspended, not revoked: they work again, if they have not expired, once the setting is switched back on. This is a change in 1.3.0: before it, the read, reply and upload routes checked the token only. See Upgrading to 1.3.0.

Notes that matter to a client

  • There is no ticket ID in any guest URL. The token names exactly one ticket, so there is nothing to enumerate.
  • The scheme is Guest, not Bearer. A guest token is not an API credential and is not accepted where one is required.
  • Every refusal about the link is the same 404 not_found. A wrong token, an unknown link, a closed ticket on a write route and a switched-off instance cannot be told apart from outside. A good link still gets other answers: 400 for an invalid body, 429 past the rate limit, and 409 reopen_window_closed for a reply or upload to a Resolved ticket after its reopen window.
  • category_id must be an active category, checked before anything is written. type_id, item_id and custom fields are not read, and the priority is always Medium.
  • guest_email must be a single bare address with no display name. It is stored lower-case.
  • The read returns a narrow view: tracking number, subject, description, status name, timestamps and the replies the guest may see. Replies carry from_you and no author. Assignee, group, reporter and internal-note data are never included, and the read has no attachment list.
  • Closing a ticket does not revoke its guest links. They keep reading the closed ticket until they expire. A resend after the ticket closed gives a read-only link, beside the older ones.
  • Submit, resend and follow-up are limited per client address, at the same budget as password sign-in (see Errors & pagination). A guest link is re-sent to a ticket at most once every five minutes; a request inside that window still answers 202.

What a requester sees

A requester is a caller with the user role. On a ticket they reported, they see its current state and its conversation, and not its history.

  • A ticket sent to a requester carries only these fields: id, tracking_number, subject, description, status_id, priority, category_id, type_id, item_id, created_at, resolved_at, assignee_user_id and resolution_notes. The group, the reporter, guest details, closed_at, updated_at, the Pending times and reopen_count are for staff and administrators. The same list applies wherever a ticket is returned, including over MCP.
  • GET /api/v1/tickets/{id}/audit, /history and /followers answer 403 forbidden to a requester on a ticket they can see (and 404 on one they cannot).
  • A requester's ticket has sla: null and can_reopen: false. A requester cannot change a ticket's status, assignment, classification or priority (403 forbidden).

OAuth clients and their service user New in 1.3.0

Creating an OAuth client also creates a service user, named after the client. The client acts as that user, at its role (staff by default, or user; never administrator). Tickets and replies a client writes carry the client's name, so a client holding tickets:write can now create tickets and replies. Before 1.3.0 those calls answered 403 user_identity_required.

  • POST /api/v1/admin/oauth-clients returns the service user's user_id. GET /api/v1/admin/oauth-clients returns user_id and groups for each client. A client sees tickets by its service user's groups, so a client whose user is in no group sees nothing when ticket scope enforcement is on.
  • The user is listed on GET /api/v1/admin/users with service_account: true. An administrator can rename it (which renames the client), change its role between staff and user, give it groups, and disable it. Disabling the user stops the client.
  • A service user never signs in. An administrator can rename it, disable it, give it groups and set its role to staff or user. A change of its email, the administrator role or reset_mfa: true on PATCH /api/v1/admin/users/{id} answers 409 service_account and applies none of the request. DELETE /api/v1/admin/users/{id} on one also answers 409: delete the client instead, which removes its user. Tickets it wrote keep its name.
  • A service user is never emailed, and an API key or OAuth client cannot follow a ticket (403 session_required).
  • GET /api/v1/admin/users returns the newest 200 accounts unless you send page. With page (1-based) it takes per_page (default 50, at most 200), q, role and service_account, and the total comes back in the X-Total-Count header.

Priority and following

  • Changing priority. PATCH /api/v1/tickets/{id} takes priority (critical, high, medium or low) beside the status, assignment and classification fields. Staff and administrators only; a requester gets 403 forbidden. Changing it re-matches the ticket's SLA policy for the new priority and keeps the SLA clock. An unknown value answers 400 bad_request, and a Resolved or Closed ticket answers 409 ticket_closed with nothing saved.
  • Reopening. A move from Resolved or Closed back to an open status is a reopen: reopen_count goes up by one, the first reopen raises the priority one level, and the SLA starts over. This holds for PATCH with a status_id, for POST /api/v1/tickets/{id}/reopen and for a requester's reply to a Resolved ticket.
  • Followers. PUT and DELETE /api/v1/tickets/{id}/follow start and stop following a ticket for the signed-in staff member or administrator, and answer 204. GET /api/v1/tickets/{id}/followers lists who follows it. Following is a personal choice, so an API key or OAuth client gets 403 session_required.
  • Archived classification. Nobody, staff and administrators included, may file a new ticket into an archived category, type or item, or reclassify one into it: 400 bad_request. A ticket already in an archived category, type or item can keep it.

Filing a ticket for someone else

POST /api/v1/tickets takes reporter_user_id (an existing account) or reporter_email (a typed address), for staff and administrators only, and at most one of them. A requester who sends either is refused with 403. The staff member is recorded as the actor.

  • A typed address is filed like a guest ticket and the guest link is emailed to it. guest_name is required with every reporter_email (400 without one), whether or not the address has an account, so a refusal says nothing about the address; it is ignored for an account. guest_phone is optional. The request is refused with 400 while guest submission is off and the address has no account. If the address belongs to an account, the ticket is filed for that account.
  • Rate limit: 40 uses of reporter_email an hour per staff member, then 429 rate_limited with Retry-After. Every reporter_email that passes validation counts, account or not, and the refusal for guest submission being off counts too; a request refused by validation spends nothing, and a unit, once taken, is never given back. reporter_user_id does not count. An API key or OAuth client counts against the user it acts as. The limit is kept in memory by each server instance.
  • Finding a user: GET /api/v1/users/lookup?q= returns at most ten accounts (id, display_name, email) whose name or address contains q. q must be at least two characters (400 otherwise). It is for staff and administrators in a signed-in session only: an API key or OAuth client gets 403 session_required, whatever scopes it holds. Disabled, deleted and service accounts are not returned. A script that files for someone sends reporter_email and lets the server resolve it (an account if the address has one, otherwise a guest ticket); an administrator's key that searched accounts can use GET /api/v1/admin/users?page=1&q=.
  • GET /api/v1/tickets/{id} carries requester (name and email) for staff and administrators, and never for requesters.

Webhook events

A webhook subscribes to event names, set with events on /api/v1/admin/webhooks. The names are * (all), ticket.created, ticket.assigned, ticket.status_changed, ticket.replied, ticket.note_added, ticket.resolved, ticket.closed, ticket.reopened, ticket.linked, ticket.priority_changed and ticket.classified. A change to a ticket is one event, and a hook gets one delivery per change, labelled with the first name it subscribes to that the change carries. The raw body holds ids only. When a change is announced under several names, a receiver that reads only Type can miss one; read the ticket by TicketID to know more. For a new ticket that auto-assignment routes, the ticket.assigned delivery has a null ActorID. Assigning a ticket to who and what it already has announces nothing. A webhook's delivery history (/api/v1/admin/webhooks/{id}/deliveries) shows a retry that was dropped as result: "dropped" with a drop_reason; see the API reference. See Webhooks in the admin guide for the order of names and the chat messages, and the API reference for the request fields.

Errors & pagination

Error format

Most error responses share one JSON shape:

{
  "error": {
    "code":    "bad_request",
    "message": "subject is required"
  }
}

Match on code, not on message. Refusals made by the authentication and role checks (401 unauthorized, and 403 with forbidden, mfa_required, password_change_required, insufficient_scope or session_required) carry the same envelope but are sent as text/plain. An unknown path answers 404 with the plain text 404 page not found.

Client mistakes answer 4xx, and DELETE of an unknown id answers 404 Changed in 1.3.0

The admin routes used to answer 500 internal_error for several ordinary mistakes by the caller, and answered 204 when asked to delete something that was not there. As of 1.3.0:

  • DELETE of an id that does not exist answers 404 not_found, not 204, on every route that deletes one of: a group, a group member, a group scope, an API key, an OAuth client, a webhook, a category, a type, an item, a custom-field assignment, an SLA policy or a canned response. Deactivating (DELETE /api/v1/admin/tags/{id}) or restoring (POST /api/v1/admin/tags/{id}/restore) a tag that does not exist answers 404 too; deactivating a tag that is already deactivated, or restoring one that is already active, still answers 204. A script that deletes the same thing twice now gets 404 the second time. This is a breaking change. Deleting a status already answered 404.
  • A NUL character in a ticket's subject, description, guest_name or guest_phone, or in a reply body, answers 400 bad_request (it used to be 500). Every other character is stored as given.
  • A canned response whose category or type is unknown, or does not belong together, answers 400 bad_request, not 500.
  • An unknown id in the path answers 404 not_found: reading, changing, or listing or adding the members and scopes of a group that does not exist (listing used to return an empty array), reading a category or changing a category, type or item that does not exist, creating a type or item under a parent that does not exist, and changing a plugin or webhook that does not exist. Downloading, or asking for a reputation re-check of, an attachment that does not exist answers 404 too.
  • An invalid value answers 400: a blank group name, a blank category, type or item name, and a zero or missing user_id or category_id in a body (bad_request), or an id in a body that names nothing (invalid_reference).
  • A conflict answers 409: a group name that is already taken (group_name_taken), and deleting a category, type or item that is still in use (category_in_use, type_in_use, item_in_use). A category is also in use while an SLA record, left by a ticket that has since moved elsewhere, still belongs to one of its SLA policies.

A client that treated 204 on a repeated DELETE as success, or retried on 500, needs to handle these codes. See Upgrading to 1.3.0.

Pagination

Two list endpoints are paged, GET /api/v1/tickets and GET /api/v1/admin/audit. Both take limit (default 100, maximum 200) and offset. A limit above the maximum is clamped rather than rejected, and a non-numeric or non-positive value is ignored, so the default applies.

  • The ticket list is a bare JSON array with no total. Page until a response is shorter than limit.
  • The audit list returns an object with entries, total, total_capped and has_more. Page while has_more is true. When total_capped is true, total is the cap (10,000) and means "at least this many".
GET /api/v1/tickets?limit=50&offset=100

GET /api/v1/tickets also takes scope: mine (the default), unassigned, all (administrators only) and visible. scope=visible is available to staff and administrators and returns every ticket the caller can see, in one query that pages with limit and offset: every ticket for an administrator, or for staff while Limit staff to their group scope is off, and the staff scope while it is on. A reporting user still gets only their own tickets. A server older than this release ignores an unknown scope and answers as mine.

Every other list returns its whole result as a bare JSON array.

Rate limiting

The application applies these limits itself. The budget is AUTH_RATE_LIMIT_PER_MINUTE (default 10 a minute). The shipped Docker Compose file passes it to the app, so under Compose you set it in .env. The wait that follows an exhausted budget is AUTH_THROTTLE_DELAY (default 1 second), passed the same way.

  • Wrong current passwords on PATCH /api/v1/me/password are counted per account against a budget the size of sign-in's (a separate counter). Over budget, the request waits for AUTH_THROTTLE_DELAY and answers 429 rate_limited with Retry-After. The correct password always works.
  • Password sign-in is limited per submitted email address. Only failed attempts count. Past the budget, further attempts answer 429 rate_limited with Retry-After. Each login for an account over its budget is also held for about a second before the password is checked, so a guesser is slowed down while a correct password still works.
  • Signup is limited per source address.
  • Guest submission, resend and follow-up are limited per source address.
  • Second-factor codes lock after five failed codes, for 15 minutes. The count is kept on the user record, so it survives a restart and is not multiplied by the number of replicas.

For broader limits, put a reverse proxy in front of the application.
