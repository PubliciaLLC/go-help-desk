REST API

How the API works. For every endpoint, parameter and schema, see the API Reference.

Browse the API Reference →

The REST API is mounted at /api/v1/. Requests and responses are JSON, except where a route takes a multipart upload, returns a file, or returns another format; the reference marks those. Timestamps are RFC 3339 strings. Resource IDs are UUIDs.

Tickets also carry a human-readable tracking number such as GHD-2026-000001. The prefix (GHD) is the ticket_prefix setting, so your instance may use another. GET /api/v1/tickets/{id} accepts a tracking number in place of the UUID. Every other ticket route takes the UUID only: for a ticket you can see, a tracking number there answers 400. See Visibility & tracking numbers.

Base URL

https://<BASE_URL>/api/v1

Quick example

curl https://helpdesk.example.com/api/v1/tickets \
  -H "Authorization: ApiKey GHD_…"

The key needs the tickets:read scope. Without it the same request returns 403.

Authentication

MethodHow to authenticateBest for
Session cookie POST to /api/v1/auth/local/login. The server sets an HttpOnly ghd_session cookie, and browsers send it on later requests. SAML and OIDC sign-in create the same kind of session. A session that has passed the password but not its second factor (a TOTP code or a passkey) is refused with 403 mfa_required on routes that need one. The built-in React SPA
API key Authorization: ApiKey GHD_<64 hex characters>. The GHD_ prefix is part of the token. It is shown once, when the key is created. The key acts at its owner's role, counts as having passed MFA, and is limited to its scopes. Scripts, CLI tools, CI pipelines, monitoring
OAuth2 JWT POST to /api/v1/auth/oauth/token with "grant_type": "client_credentials", client_id and client_secret. The token lasts one hour (expires_in: 3600). Send it as Authorization: Bearer <token>. A client acts at the staff role, so it cannot reach admin-only routes. Deleting the client revokes its tokens on the next request. Server-to-server integrations (JIRA, chatbots)

The MCP server at /mcp/ accepts the same session, API key and OAuth2 JWT authentication as the REST API. See MCP Server for connection details.

Scopes

API keys and OAuth clients carry scopes. A session does not need them. A credential acts at its owner's role (for an API key) or at the staff role (for an OAuth client), and its scopes narrow that further. A scope never widens what the role allows.

A scope is resource:read or resource:write, and write implies read on the same resource. The resources are:

  • tickets, users, groups, categories, tags, canned_responses, sla, settings, plugins, webhooks and credentials: read and write.
  • audit: read only. No credential can write the audit log. The admin audit view needs audit:read; tickets:read does not reach it.
  • There is no wildcard. * and tickets:* grant nothing.
  • An empty list denies everything. Creating a key or an OAuth client without scopes answers 400 scopes_required. An unknown scope answers 400 invalid_scope.
  • A credential cannot grant a scope it does not hold itself, which answers 403 insufficient_scope. A request outside the credential's scopes gets the same answer.

The catalogue is served by GET /api/v1/admin/scopes, which needs credentials:read. Credentials issued before scopes were enforced (1.2.0) carry none and stop working until they are reissued. See Upgrading to 1.2.0.

Settings that need a signed-in administrator

An API key or OAuth client cannot change these settings, whatever scopes it holds. The settings endpoint answers 403 session_required. The SAML and OIDC configuration routes, a user's own password and MFA enrolment, and the MFA and passkey sign-in routes refuse machine credentials the same way. Repointing an identity provider, switching off MFA or opening registration would each give whoever holds the key a session they should not have.

The settings a machine credential cannot change are:

  • Sign-in: saml_enabled, saml_metadata_url, saml_cert_pem, saml_key_pem, oidc_enabled, oidc_issuer_url, oidc_client_id, oidc_client_secret, oidc_redirect_url.
  • Second factor: mfa_enabled, mfa_enforced_roles.
  • Accounts: self_signup_enabled, open_registration_enabled, allowed_email_domains.
  • Guests: guest_submission_enabled.
  • Closed tickets and audit: closed_reopen_policy, audit_mask_requester_names, audit_retention_days, staff_can_view_ticket_change_history.
  • Attachment scanning: attachment_scan_address, attachment_scan_policy, attachment_allowed_types, attachment_infected_handling, attachment_mismatch_handling.
  • Reputation lookups: attachment_reputation_refresh, attachment_reputation_virustotal_enabled, attachment_reputation_virustotal_key, attachment_reputation_metadefender_enabled, attachment_reputation_metadefender_key, attachment_reputation_polyswarm_enabled, attachment_reputation_polyswarm_key, attachment_reputation_circl_enabled.
  • Deprecated, still writable: attachment_vt_lookup, attachment_vt_api_key, attachment_reputation_provider, attachment_reputation_api_key.

Visibility and tracking numbers

A ticket you may not see answers 404 not_found, the same answer as a ticket that does not exist. It is never 403, so tracking numbers, which are sequential, cannot be walked to learn which tickets exist. Earlier releases answered 403; from 1.3.0 the answer is 404.

GET /api/v1/tickets/{id} accepts a tracking number in any letter case, so ghd-2026-000001 and GHD-2026-000001 reach the same ticket. There is no separate lookup endpoint. Every other route under /api/v1/tickets/{id} takes the UUID, and answers 400 for a tracking number of a ticket you can see.

Closed tickets

Closed is read-only and terminal by default. Nothing moves a closed ticket back to an open state unless the closed_reopen_policy setting allows the caller's role. The values are off (the default, nobody may reopen), admin (administrators only) and staff_admin (staff and administrators). A requester never reopens a ticket.

  • A requester's reply, upload or update to a closed ticket answers 409 ticket_closed. Staff and administrators can still post replies to a closed ticket.
  • A reopen the policy does not allow answers 409 ticket_closed, with a message that says why.
  • POST /api/v1/tickets/{id}/follow-up opens a new ticket linked to a closed one, and answers 201 with the new ticket. Staff and administrators can open one for any closed ticket they can see; a requester can open one for their own. A ticket that is not closed answers 409 ticket_not_closed, and a second follow-up of the same ticket answers 409 follow_up_exists.
  • A requester's reply to a Resolved ticket after the reopen window answers 409 reopen_window_closed.
  • A guest's write to a closed ticket answers 404 not_found. A guest opens a follow-up with POST /api/v1/guest/follow-up.

Attachment downloads

Attachments are download-only. GET /api/v1/tickets/{id}/attachments/{attachId} streams the file with these headers:

Content-Type: application/octet-stream
Content-Disposition: attachment; filename="…"
Vary: Sec-Fetch-Dest
Cache-Control: private, max-age=3600

The content type is always application/octet-stream, whatever the file claims to be. No browser renders that type, so a file opened from the link is saved, not shown. The header check below covers browsers that request a file to display it. It cannot stop a script that fetches the bytes and renders them itself.

The route checks Sec-Fetch-Dest. Only document, empty and an absent header are accepted. A request whose header says the browser will render the response, such as an image or a frame, is refused with 403 not_downloadable. Command-line clients send no such header and are not affected. An <a download> click and a fetch() send empty and are accepted.

Uploads, the attachment object and the reputation fields are described in the API Reference. For why the help desk never renders an attachment, see Attachment Security.

Guest access

Guests reach six routes under /api/v1/guest. None takes a session, an API key or an OAuth token.

  • POST /guest/tickets submits a ticket. The body has subject, description, category_id, guest_email and guest_name (the last two are required), and optionally guest_phone. It answers 201 with the tracking number and nothing else. The access link goes by email.
  • POST /guest/resend asks for a new access link, given a tracking number and an address. It answers 202 whether or not anything matched.
  • GET /guest/ticket, POST /guest/replies, POST /guest/attachments and POST /guest/follow-up take the guest token and act on the one ticket it names.

Turning guest_submission_enabled off makes the submit, resend and follow-up routes answer 404. The read, reply and upload routes check the token only, not the setting, so a link already sent keeps working on those routes.

Notes that matter to a client

  • There is no ticket ID in any guest URL. The token names exactly one ticket, so there is nothing to enumerate.
  • The scheme is Guest, not Bearer. A guest token is not an API credential and is not accepted where one is required.
  • Every guest refusal is the same 404 not_found. A wrong token, an unknown link, a closed ticket on a write route and a switched-off instance (for the routes that check it) cannot be told apart from outside.
  • category_id must be an active category, checked before anything is written. type_id, item_id and custom fields are not read, and the priority is always Medium.
  • guest_email must be a single bare address with no display name. It is stored lower-case.
  • The read returns a narrow view: tracking number, subject, description, status name, timestamps and the replies the guest may see. Replies carry from_you and no author. Assignee, group, reporter and internal-note data are never included, and the read has no attachment list.
  • Closing a ticket does not revoke its guest links. They keep reading the closed ticket until they expire. A resend after the ticket closed gives a read-only link, beside the older ones.
  • Submit, resend and follow-up are limited per client address, at the same budget as password sign-in (see Errors & pagination). A guest link is re-sent to a ticket at most once every five minutes; a request inside that window still answers 202.

Errors & pagination

Error format

Most error responses share one JSON shape:

{
  "error": {
    "code":    "bad_request",
    "message": "subject is required"
  }
}

Match on code, not on message. Refusals made by the authentication and role checks (401 unauthorized, and 403 with forbidden, mfa_required, insufficient_scope or session_required) carry the same envelope but are sent as text/plain. An unknown path answers 404 with the plain text 404 page not found.

Pagination

List endpoints take limit (default 100, maximum 200) and offset. A value above the maximum is clamped rather than rejected, and a non-numeric value is ignored, so the default applies.

Most lists return a bare JSON array with no total. Page until a response is shorter than limit.

GET /api/v1/tickets?limit=50&offset=100

Two kinds of list differ:

  • GET /api/v1/admin/audit returns an object with entries, total, total_capped and has_more. Page while has_more is true. When total_capped is true, total is the cap (10,000) and means "at least this many".
  • Some lists are not paged at all. The reference says which.

Rate limiting

The application applies these limits itself. The per-address budget is AUTH_RATE_LIMIT_PER_MINUTE, which is 10 a minute by default.

  • Password sign-in is limited per submitted email address. Only failed attempts count. Past the budget, further attempts answer 429 rate_limited with Retry-After. Each login for an account over its budget is also held for about a second before the password is checked, so a guesser is slowed down while a correct password still works.
  • Signup is limited per source address.
  • Guest submission, resend and follow-up are limited per source address.
  • Second-factor codes lock after five failed codes, for 15 minutes. The count is kept on the user record, so it survives a restart and is not multiplied by the number of replicas.

For broader limits, put a reverse proxy in front of the application.
