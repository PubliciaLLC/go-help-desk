Upgrading to 1.3.0

A feature release. Most of it is new ground; a handful of changes touch something an existing install or integration relies on. Read this before you upgrade, not after.

If your Docker Compose install scans attachments with the bundled ClamAV, scanning stops on upgrade when your docker/.env has no CLAMAV_ADDR line. Once the instance holds an attachment, administrators see an amber Attachments are not being scanned banner that says so. To keep scanning, add COMPOSE_PROFILES=antivirus and CLAMAV_ADDR=tcp://clamav:3310 to docker/.env and run docker compose up -d. See ClamAV is opt-in.

Coming from 1.1.x? Read Upgrading to 1.2.0 as well; every item there applies too.

Everything below is additive unless it says otherwise. Each item names who notices.

What's new in 1.3.0

  • Passkeys. Passkeys and hardware security keys work as a second factor, beside authenticator apps. A passkey is checked after the password, never instead of it. Second factor
  • An Account page. Change your password, set up an authenticator app, add and remove passkeys, and verify a second factor.
  • Recovery from lost factors. The reset-factors <email> subcommand of the server binary clears every second factor from one account, so its owner can sign in with their password and enrol again. It is run on the server, not through the web. In the Compose stack: docker compose exec app /app/server reset-factors <email>.
  • OpenID Connect sign-in is documented. OIDC works beside SAML and local accounts, and is set up under Admin → Settings → Authentication → OIDC / OpenID Connect. It has shipped since 1.1.1, but its setup was not documented on this site and no release notes announced it. Only an address the provider marks as verified is used to match or create an account. OIDC
  • Refused sign-ins say why. When a single sign-on is refused, the login page shows a plain message for the reason, such as an address already held by another account or a domain that is not allowed. The message is chosen from the refusal code, never from text in the address bar.
  • Provider-wrapped addresses are matched. On a first OIDC sign-in, the address is matched by its parsed form, so an address sent as <a@example.com> finds the account for a@example.com instead of creating a second one. The sign-in is refused instead when that account is an administrator, or is already linked to SAML or to another OIDC identity.
  • Identity-provider lockout guard. A SAML or OIDC settings change that would leave no administrator able to sign in is refused. Design notes
  • Signup asks later. The display name and password are chosen when the email is verified. Details
  • Guest submission works. A visitor files a ticket at /submit without an account, receives a per-ticket link, and can reply through it. Attaching a file is possible only through the API. The guest page has no upload control, and that is not available in 1.3.0. Tracked in #445. Guest access
  • Closed means closed. A closed ticket is read-only and stays closed by default. The way on is a linked follow-up ticket. An operator can allow admins, or staff and admins, to reopen a closed ticket. Follow-up tickets
  • The lifecycle runs itself. An auto-close sweep runs every five minutes. A reopen window of 0 closes a resolved ticket on the next sweep.
  • SLA tracking end to end. Timers pause while a ticket is Pending, a breach sweep runs, and the indicators are colour-coded. The switch is under Admin → Settings.
  • Reporters can attach files to replies. Details
  • Works on a phone. Staff triage and reporters can use the app on a phone. Administration stays on the desktop. Design notes
  • First-run setup creates a category. A new instance can file a ticket straight away. First-run setup
  • A readable audit log. A per-ticket activity feed and an admin-wide searchable view. Audit log
  • Notifications from an outbox. Email is queued in the database and retried after 30 seconds, doubling each time, up to eight attempts. Webhooks are queued too, but each one is sent once and never retried; the Webhooks screen shows each hook's last delivery result.
  • Webhooks with chat formats. An Admin → Webhooks screen, with Slack, Teams, Discord and JIRA payload formats. Webhooks
  • Attachment security. Content detection, mismatch handling, quarantine, download-only files, and optional scanning and reputation lookups. Attachment Security
  • Published images. Multi-architecture images for amd64 and arm64, published to GHCR. Building from source is still supported. Quick start
  • Loud configuration warnings. Example secrets are reported at startup and in a red banner for administrators. "Scanning is off" is reported at startup, by GET /api/v1/admin/security-warnings and, on an instance that holds attachments but never chose a scan policy, in an amber banner. An attachment directory that cannot be written is reported at startup and in a red banner. Admin → Settings → Attachments → Malware scanning shows the scanner's status.

ClamAV is opt-in

Docker Compose used to start the bundled ClamAV scanner and set CLAMAV_ADDR for you. From 1.3.0 it is opt-in (#297). An install that relied on that, and whose docker/.env has no CLAMAV_ADDR line, stops scanning attachments on upgrade. Nothing else changes.

Administrators are told. When no scan policy has ever been saved, no scanner address is set (in Settings or in CLAMAV_ADDR) and the instance already holds at least one attachment, administrators see an amber banner at the top of every page:

Attachments are not being scanned. To turn scanning back on, add COMPOSE_PROFILES=antivirus and CLAMAV_ADDR=tcp://clamav:3310 to docker/.env, run docker compose up -d, then confirm the scanner address under Settings → Attachments. To keep scanning off, choose "Do not scan" there.

The server also logs attachment scanning is OFF: no scanner address is configured at startup (#303), and GET /api/v1/admin/security-warnings reports Attachments are not scanned. Uploads are accepted without being checked. Admin → Settings → Attachments → Malware scanning now starts with a status block: the policy, whether an address is configured, whether the scanner answers, and what that means for uploads. Nothing stops the upgrade, but the banner will be there when you sign in. To keep scanning on, do what it says:

  1. Add the two lines to your own docker/.env (they are commented out in the "Virus scanning" section of docker/.env.example): 
    COMPOSE_PROFILES=antivirus
CLAMAV_ADDR=tcp://clamav:3310
  2. Run docker compose up -d in docker/.
  3. Confirm the scanner address under Admin → Settings → Attachments → Malware scanning. A value saved there takes precedence over CLAMAV_ADDR. The status block shows Reachable: Yes once ClamAV has finished downloading its signatures.

The banner goes away when a scanner address is set, or when you choose a scan policy there, Do not scan included. Choose that to keep scanning off on purpose; the banner does not return.

clamav/clamav is published for linux/amd64 only. On Apple Silicon the scanner runs under emulation rather than failing to pull.

Once CLAMAV_ADDR is set, uploads are refused with 503 while the scanner cannot be reached. That covers the first few minutes after the first start, while the scanner downloads its signature database (about 300 MB). Everything other than attachment upload keeps working.

See Getting Started → Virus scanning.

The audit log is readable, and still kept forever

Entries were written before 1.3.0, but nothing could read them. From 1.3.0 there is a per-ticket activity feed and an admin-wide searchable view.

Nothing is deleted unless you ask. audit_retention_days defaults to 0, which keeps everything. To start pruning, set it to a number of days under Admin → Settings. The maximum is 36,525 days, a century. Set it back to 0 to keep everything again. The first sweep runs two minutes after the server starts, then once a day, so an instance that restarts more often than daily still prunes. Only a signed-in administrator can change this setting. An API key cannot, because shortening retention destroys evidence rather than merely widening access.

Staff see the per-ticket feed. The field-level before and after diff is behind a second setting, staff_can_view_ticket_change_history. It is off by default, so no instance starts showing staff something it did not show them in 1.2.0.

A machine credential needs the audit:read scope to read the admin-wide view.

See Admin Guide → Audit log.

Signup asks for the name and password when the email is verified

Before this change, anyone who knew an address could sign up again after its owner, with a password or name of their own. The owner, clicking the newest link, got an account with it. The signup form now asks only for the email address. The link in the email opens a page that asks for the display name and the password.

For API clients:

  • POST /api/v1/auth/verify-email requires token, display_name and password. A request with a missing or invalid name or password is refused with display_name_required, password_too_short or password_too_long, and the link is not used up.
  • A display_name or password sent to POST /api/v1/auth/signup is ignored.
  • GET /api/v1/auth/verify-email?token= returns the email address the link is for.

Signups still pending at upgrade keep working. Their links now ask for a name and a password.

guest_submission_enabled requires a signed-in administrator

This setting decides whether anonymous people can file tickets. It also decides whether the category list can be read without signing in. An API key with settings-write scope could previously switch it either way. Now only a signed-in administrator can change it. An API key cannot, whatever scopes it holds. The refusal is 403 session_required.

A malformed or null value is refused outright, rather than being read back as false.

See the API settings that need a person.

Reporters can attach files to replies

The upload API never checked the role. Any signed-in user who could see a ticket could already attach a file to it. The reply composer offered the control to staff only. A reporting user replying to their own ticket now sees the same Add files control that staff have.

Building from source needs Docker Buildx

Building the image yourself with docker compose -f docker-compose.yml -f docker-compose.build.yml up -d --build needs the docker buildx CLI plugin. Without it, on Apple Silicon and other hosts that are not amd64, the build fails at its first step with a --platform= parse error. A later attempt to work around that produced an image that builds cleanly and does not run, so it was reverted.

Docker Desktop includes Buildx. If docker buildx version fails, install the plugin. The steps are under Building from source in Getting Started.

This only affects building. The quick start pulls a published image, so most people never run a builder at all.

Two environment variables are gone

MFA_ENABLED and GUEST_SUBMISSION_ENABLED were removed in 1.3.0. Nothing read them, so an instance that set them got no error and no change. MFA and guest submission are switched on under Admin → Settings, and that setting is the switch.

SLA_ENABLED still exists. It switches SLA tracking on at each start, and never off. The setting under Admin → Settings is the switch.

No SAML environment variable is read. SAML and OIDC are configured under Admin → Settings → Authentication.

A ticket you cannot see answers 404, not 403

Who notices: API clients that branch on 403.

The REST API used to answer 403 Forbidden for a ticket that exists but that the caller may not see. It now answers 404 Not Found, the same answer a tracking number that does not exist gets. Tracking numbers run in sequence, so a signed-in reporter could walk them to learn which tickets exist. This is a deliberate change to the REST API's published contract. A client that reads 403 as "this ticket exists, but not for you" will now get 404 for the same request.

See REST API → Visibility and tracking numbers.

Closed tickets stay closed for staff and admins

Who notices: staff, administrators, and automation that reopens tickets.

A Closed ticket is now read-only for everyone, staff and administrators included, unless the instance allows reopening. The setting is Reopening closed tickets, under Admin → Settings → General → Ticket lifecycle (closed_reopen_policy). It is off by default. It can allow administrators, or staff and administrators, and it never allows requesters. Until 1.3.0, staff and administrators could reopen a Closed ticket. With the setting off, the status picker, the reopen endpoint (POST /api/v1/tickets/{id}/reopen) and the MCP update_ticket_status tool all refuse to reopen one. The way on is a linked follow-up ticket.

A reopen window of 0 now closes a resolved ticket on the next auto-close sweep, about five minutes after it is resolved.

Uploads wait for the scanner, or are refused

Who notices: installs that set CLAMAV_ADDR, including bare-metal and Kubernetes installs.

Once a scanner address is set, attachment_scan_policy defaults to required. An upload is refused with 503 and a Retry-After header while the scanner cannot be reached. It is not accepted unscanned. Version 1.2.0 accepted uploads without a scan when the scanner was unreachable. To keep that behaviour, choose Scan, but accept uploads while the scanner is down under Admin → Settings → Attachments → Malware scanning. That is a choice you make, not the default.

SVG logos are refused

Who notices: instances whose logo is an SVG file.

The logo accepts PNG, JPG and GIF files, and SVG is refused. The logo is the one uploaded file the application shows inline on its own origin, where staff sessions live, and an SVG file can carry scripts. An SVG logo uploaded by an earlier release is no longer served, so the sidebar falls back to the site name. Upload a PNG, JPG or GIF under Admin → Settings → Branding.

Postgres listens on loopback only in Compose

Who notices: anything that reached the database from another machine, such as a backup job or a reporting tool.

The shipped Compose file publishes Postgres on 127.0.0.1:5432. Version 1.2.0 published it on every interface, and Docker handles a published port before the host firewall sees it, so closing the port in ufw or firewalld did not protect it. After the upgrade, only processes on the Docker host can connect. Run such tools on the host, or reach the database through an SSH tunnel.

Quoted email addresses are refused

Who notices: anyone whose address needs quotation marks, and single sign-on users whose provider sends one.

An address whose local part needs quotation marks, such as "john doe"@example.com, is refused with 400 wherever an address is saved: at signup, on a guest ticket, and when an account is created or edited. Parsing used to drop the quotes, which turned it into an address the mailer could not send to, so the person was never sent their link. Quotation marks that were never needed are dropped and the address kept: "john"@example.com is stored as john@example.com. Addresses already stored are not changed. A first sign-in through SAML or OIDC with an address that needs quotation marks creates no account, and the login page says the address cannot be used (invalid_email). An existing single sign-on user keeps the address they have.

Passwords are limited to 72 bytes

Who notices: anyone who sets a password, and API clients that set one.

A password must be 8 to 72 bytes. The limit is bcrypt's: bcrypt reads only the first 72 bytes and will not hash more. Bytes are counted, not characters, so an accented letter takes two bytes and most other non-Latin characters take three or four. A longer password is refused with a 400 that names the limit. Before 1.3.0, most paths that set a password answered with a server error (500). Sign-in applies no maximum.

Switching guest submission off suspends guest links

Who notices: guests holding a link, and administrators who switch Guest submission off.

Before 1.3.0, turning guest_submission_enabled off stopped new guest tickets and link re-requests, but a link already emailed kept reading, replying and uploading. Now it stops those too. While the setting is off, every guest route answers 404 not_found: submit, resend, and the four routes that take a link (read, reply, upload and follow-up). The answer is identical to the one for a link that never existed, so a guest cannot tell the two apart. The links are suspended, not revoked. Switch the setting back on and every link that has not expired works again. A guest who is partway through a conversation when you switch it off cannot read or reply until you switch it back on.

The switch under Admin → Settings → General → Submissions → Guest submission now says so. See Guest ticket submission and REST API: Guest access.

A half-signed-in session expires after 5 minutes

Who notices: users who take longer than that at the second-factor step, and API clients that sign in in two requests.

When a password is accepted but a second factor is still owed, the session now has a deadline: 5 minutes to enter a code or confirm with a passkey, and 15 minutes when the user must first set up their factor, because that means installing an app and scanning a code. The deadline is fixed when the password is accepted, or, for a new self-registered account, when its email address is verified. Nothing extends it. Past it, the session is deleted and the next request is refused with 401, so the user signs in with their password again. Code entry after the deadline is not checked, so it does not use up one of the five attempts. A session that has passed the second factor is not affected.

Until 1.3.0 a half-signed-in session lived as long as any other session, up to 7 days. Anyone who is partway through signing in at the moment you upgrade signs in once more. An administrator with no second factor can still recover by signing in with the password and enrolling, as before.

See Authentication: Second factor.

Passwords are hashed at bcrypt cost 12

Who notices: everyone who signs in with a password, once; and servers that take many sign-ins at the same moment.

New passwords are hashed with bcrypt at cost 12. Releases up to 1.2 used cost 10, although earlier security pages said 12. An existing hash keeps working and is replaced with a cost-12 hash the next time its owner signs in with the correct password. The replacement is best effort: if it fails, the failure is logged and the sign-in still succeeds, and the next sign-in tries again. It never overwrites a password that was changed in the meantime. An account that does not sign in keeps its cost-10 hash.

Each cost step doubles the work, so a password check takes about four times the server time it did. If many people sign in at once, check AUTH_THROTTLE_DELAY and AUTH_RATE_LIMIT_PER_MINUTE. A wrong password for an account still on cost 10 is made to cost as much as one for an address that has no account, so the change of cost does not let the response time show which addresses have accounts.

JWT_SECRET is optional

Who notices: operators; and OAuth clients, once, if the signing key changes.

JWT_SECRET signs the OAuth2 access tokens. It no longer has to be set, and Docker Compose no longer refuses to start without it.

  • If it is unset, or shorter than 32 bytes, the server generates a random 32-byte key at its first start, stores it in the database and uses it from then on. Each start logs a line beginning jwt signing key: using generated key stored in the database. Every instance that shares the database uses the same key.
  • If it is 32 bytes or more, your value is used, exactly as before.
  • If it is exactly one of the example secrets this project has published (for example change-me-in-production or dev-jwt-secret-change-me), it is ignored, a generated key is used, and the server logs a warning. A value of 32 bytes or more that only looks like a placeholder, because it contains a word such as change-me or example, is still used; the server logs an error at startup and administrators see the red insecure-configuration banner for it.

Upgrade effect. If your JWT_SECRET is 32 bytes or more and is not a published example, nothing changes. If it was short or a published example, the key in use changes at the first start, and every OAuth client fetches a new access token once. Nobody is signed out: sessions use SESSION_SECRET, not this key.

The generated key is stored in the database without encryption, so a database backup contains the key that signs OAuth2 tokens, and a restore onto another instance carries it along. To rotate it, delete the jwt_signing row from the instance_secrets table and restart; every OAuth2 access token issued before that stops working.

See Getting Started: JWT signing key.

Compose passes two more variables, and a throttle of 0 is refused

Who notices: installs that set AUTH_RATE_LIMIT_PER_MINUTE or AUTH_THROTTLE_DELAY in docker/.env, and anyone who set the delay to 0.

The shipped docker-compose.yml now passes these to the app. Until now it did not, so a value in .env did nothing:

  • AUTH_RATE_LIMIT_PER_MINUTE: default 10. Failed password attempts per account per minute before the server answers 429. 0 turns the limit off.
  • AUTH_THROTTLE_DELAY: default 1s. How long a login for an account that has used up its budget waits before the password is checked.

If you already had either in .env, it takes effect now. Every other variable on the configuration reference reaches the app, except DATABASE_URL and HTTP_PORT, which stay fixed in the file, and ATTACHMENT_DIR, which is not passed, so the app keeps its default /data/attachments, where Compose mounts the attachments directory.

AUTH_THROTTLE_DELAY is now a supported setting, and a delay of 0 (or less) is refused: the server does not start, on any kind of install, and says the delay must be a positive duration such as 1s. Without the delay, an account that has used its budget could be guessed at much faster.

Startup checks: ATTACHMENT_DIR and APP_ENV

Who notices: installs whose attachment directory cannot be written.

At startup the server checks that ATTACHMENT_DIR (default /data/attachments, which under Compose is the mounted docker/data/attachments) exists, creating it if it is missing, and that a file can be written there. If not:

  • the server logs a warning, and administrators see a red Attachment uploads are disabled banner with the reason;
  • every upload, from staff, requesters and guests, is refused with 503 attachments_unavailable until the directory is fixed. Everything else runs, and stored attachments can still be downloaded while the directory is readable;
  • the check repeats on each upload, so fixing the permissions needs no restart.

Before this, an unwritable directory showed up as a failed upload partway through, as a 500.

APP_ENV does nothing. If it is set in your environment, whatever its value, the server logs one line saying it is set and ignored. Use LOG_LEVEL for verbose logs.

Client mistakes answer 4xx, and DELETE of an unknown id answers 404

Who notices: API clients and scripts that call the admin routes. This is a breaking change to the REST API.

Several ordinary mistakes by the caller used to be answered with 500 internal_error, and a DELETE of something that was not there answered 204. Now:

  • DELETE of an unknown id answers 404 not_found for groups, group members, group scopes, API keys, OAuth clients, webhooks, categories, types, items, custom-field assignments and SLA policies. A script that deletes the same thing twice gets 404 the second time. Deleting a status already did.
  • An unknown group, category, type, item, plugin, webhook or attachment answers 404 where the route names it. Listing the members or scopes of an unknown group answers 404 instead of an empty array.
  • A blank group, category, type or item name, and a zero or missing user_id or category_id, answer 400. An id in a body that names nothing answers 400 invalid_reference.
  • A group name that is already taken answers 409 group_name_taken. Deleting a category, type or item that is still in use answers 409 category_in_use, type_in_use or item_in_use.

Treat a 404 on DELETE as "already gone" if your script needs to be idempotent. See REST API: Errors.

Email needs encryption to send a password, and says when it is off

Who notices: anyone whose mail server does not offer encryption, or whose SMTP_USER is set for a server that does not log in. Read this one before you upgrade.

There is no new setting. The rule depends on the port and on whether SMTP_PASSWORD is set:

  • Password set: the connection must be encrypted. Port 465 is encrypted from the first byte. Any other port must offer STARTTLS. A password is never sent unencrypted, even to a private address.
  • No password: unencrypted mail is allowed only to a server on a loopback or private address (10.x.x.x, 172.16 to 172.31, 192.168.x.x, or IPv6 fc00::/7). A public address still needs encryption.

Nothing needs changing if your mail server offers STARTTLS (or you use port 465) and, when SMTP_USER is set, offers AUTH. What now fails:

  1. A relay on localhost that takes a password without encryption. The send fails with SMTP server does not offer STARTTLS, and SMTP_PASSWORD is set: refusing to send the password unencrypted. Turn on STARTTLS (or TLS on port 465) on the relay, or drop the password if the relay does not need one for your network.
  2. Mail without a password to a public server that has no STARTTLS. The send fails with SMTP server does not offer STARTTLS and is not on a private address: refusing to send mail unencrypted. Use a server that offers STARTTLS, or port 465.
  3. SMTP_USER set, but the server offers no AUTH. The send fails with SMTP server does not offer AUTH but SMTP_USER is set. Before, the mail was sent without logging in. Point at a server that offers AUTH, or remove SMTP_USER and SMTP_PASSWORD if the relay accepts your mail without a login.
  4. Turning on self-signup or guest submission while email is off. Saving the setting is refused with 400 email_required when SMTP_HOST or SMTP_FROM is unset. An install that already has either one on is not switched off and can still save other settings; it gets a warning in the admin panel instead.
  5. A damaged email template. The message is marked failed at once, with no retries, and the error shows in the admin email warning. The shipped templates render, so this matters only for a damaged build.

Port 465 now connects with TLS from the first byte. Before, it waited until the timeout, so no working setup changes.

How you see it. A failed send is retried for about an hour (a template error is not retried) and then marked failed. While any message is retrying, or failed within the last day, administrators see an email warning with the newest error, with any address replaced by [address]. The same warning lists which of SMTP_HOST and SMTP_FROM is unset, and whether signup or guest submission is on with email off. The server log says once at startup whether email is enabled, and warns when only one of the two is set. The warning is also in GET /api/v1/admin/security-warnings, as email.

Accounts on an old password hash must reset after 30 days

Who notices: people who rarely sign in (seasonal staff, requesters), and API clients that sign in with a password.

Passwords are now hashed more strongly (see Passwords are hashed at bcrypt cost 12). An account is upgraded the next time its owner signs in. An account that has not signed in within 30 days of the first start of 1.3.0 must reset its password. Until it does, a correct password on an old hash is refused with 403 password_reset_required and the message Your password was saved in an older, weaker form and must be reset before you can sign in.

  • The clock starts when 1.3.0 first runs against the database. It is recorded once.
  • The number of days is under Admin → Settings → Authentication → Passwords (password_rehash_grace_days). The default is 30, and it can be 1 to 365. Changing it moves the deadline for everyone.
  • Administrators are exempt, so an instance cannot lock itself out. They are upgraded at their next sign-in like everyone else. Staff and requesters are refused. When SAML limits password sign-in to administrators, other people get the SAML refusal instead.
  • How a person resets: an administrator sets a new password for them (Admin → Users, open the person, Reset password). The sign-in page cannot send a reset email in 1.3.0 (see What is not in 1.3.0).

Tell the people who sign in rarely, or have an administrator reset them, before day 30. New installs are not affected.

Unlock an account from the server

Who notices: nobody, until someone is locked out. This is new.

The server binary has a second recovery command beside reset-factors. In the Compose stack:

docker compose exec app /app/server unlock you@example.com

It works when the web cannot: a lost authenticator or passkey, a disabled account (the only administrator included), a used-up second-factor lockout, or an administrator who signs in through single sign-on and has no usable password. In one step it clears every second factor, turns the account back on, clears the second-factor lockout, ends all sessions, and sets a new random password that it prints once. The person must choose a new password at their next sign-in. The command is recorded in the audit log with the server console as the actor. It needs shell access to the server and adds nothing reachable from the network. reset-factors is unchanged and still does only the factor part.

A signed-in session that owes a password change is answered 403 password_change_required everywhere except PATCH /api/v1/me/password. POST /api/v1/auth/local/login reports it as password_change_required, and the user record carries must_change_password. See Getting Started: Locked out?.

An IP address or one-word BASE_URL turns passkeys off

Who notices: installs reached by an IP address or a host name with no dot, and anyone whose only second factor is a passkey.

Passkeys are tied to a domain name, so they work only when the host in BASE_URL is a domain name (help.example.com) or localhost. If it is an IP address (http://192.168.1.10:8080), a single word (http://helpdesk:8080) or has non-ASCII characters, passkeys are switched off. The server still starts, logs passkeys unavailable once, and administrators see a warning banner that explains it.

  • The passkey routes answer 503 passkeys_unavailable. GET /api/v1/auth/providers reports passkeys: false, and GET /api/v1/admin/security-warnings carries passkeys with available and reason.
  • An account whose only second factor is a passkey cannot sign in while passkeys are off. Sign-in answers 403 passkey_unavailable and tells the person to ask an administrator to reset their sign-in factors. After Reset MFA, they sign in and enrol an authenticator app. Accounts with an authenticator app are not affected. For the last administrator, run reset-factors or unlock on the server.
  • Passkeys registered under a domain that you later fix work again if the domain matches.

A BASE_URL with a non-ASCII host stops the server from starting. Write it in punycode.

MCP refuses requests from another origin

Who notices: browser-based MCP clients, and reverse proxies that add an Origin header. Streamable HTTP at /mcp is new; the older SSE routes stay.

Every MCP route (/mcp, /mcp/sse, /mcp/message and anything else under /mcp/) answers 403 origin_not_allowed when the request carries an Origin header that is not the origin of your BASE_URL. This is checked before sign-in. Requests with no Origin header, which is what SDKs, editors and curl send, are unaffected. Serve a browser client from the BASE_URL origin, or stop the proxy adding the header.

1.2.x accepted these requests on the SSE routes. The change closes a way for a web page on a sibling site to act through a signed-in user's session cookie. Upgrade if you expose MCP over SSE. See MCP Server.

A public reply through MCP now emails the requester

Who notices: anyone with an AI agent or other tool connected over MCP.

A public reply posted through the MCP add_reply tool used to be saved and never emailed. It now emails the requester (the guest, with a guest link, or the reporting account), the same as a reply through the REST API. Anything connected over MCP can now send mail to your customers. Review which credentials have tickets:write before you upgrade. Internal notes (internal: true) still send nothing, and MCP has no notify_customer switch: use an internal note for anything that should not reach the requester.

One change for staff over both REST and MCP: a staff member or administrator who replies publicly on a ticket they filed themselves is no longer emailed a copy of their own reply. Webhook receivers see it too, as an empty reporter_email in the raw payload. An ordinary user replying on their own ticket still gets the copy.

Doing the upgrade

  1. Take a database backup. Migrations are forward-only; there is no automatic rollback.
  2. If you scan attachments with the bundled ClamAV, add the two lines to docker/.env and run docker compose up -d. The amber Attachments are not being scanned banner tells you if you need to. See ClamAV is opt-in.
  3. Update and restart. 
    cd go-help-desk
git pull
cd docker
docker compose pull
docker compose up -d
    If you checked out a tag earlier (for example v1.2.0), run git checkout main before git pull. If you build from source, run the build command from Building from source instead of the two docker compose commands. Migrations run automatically on startup, before the server accepts traffic.
  4. Sign in as an administrator. Look for the red insecure-configuration banner, the red Attachment uploads are disabled banner and the amber scanning banner, and check the scanning status under Admin → Settings → Attachments → Malware scanning. Decide audit_retention_days and whether staff should see the field-level change history (staff_can_view_ticket_change_history).
  5. If you have API clients that drive signup, update them for the new verification request.
  6. If you have scripts that call admin DELETE routes, or that drive sign-in in two requests, or that fetch OAuth tokens, see the 404 and 4xx changes, the 5-minute session and the JWT key.

For the general mechanics, including zero-downtime upgrades, see Getting Started → Upgrading.
