Upgrading to 1.3.0

A feature release. Most of it is new ground; a handful of changes touch something an existing install or integration relies on. Read this before you upgrade, not after.

If your Docker Compose install scans attachments with the bundled ClamAV, scanning stops on upgrade when your docker/.env has no CLAMAV_ADDR line. Add two lines to docker/.env to keep it. See ClamAV is opt-in.

Coming from 1.1.x? Read Upgrading to 1.2.0 as well; every item there applies too.

Everything below is additive unless it says otherwise. Each item names who notices.

What's new in 1.3.0

  • Passkeys. Passkeys and hardware security keys work as a second factor, beside authenticator apps. A passkey is checked after the password, never instead of it. Second factor
  • An Account page. Change your password, set up an authenticator app, add and remove passkeys, and verify a second factor.
  • Recovery from lost factors. The reset-factors <email> subcommand of the server binary clears every second factor from one account, so its owner can sign in with their password and enrol again. It is run on the server, not through the web. In the Compose stack: docker compose exec app /app/server reset-factors <email>.
  • OpenID Connect sign-in is documented. OIDC works beside SAML and local accounts, and is set up under Admin → Settings → Authentication → OIDC / OpenID Connect. It has shipped since 1.1.1, but its setup was not documented on this site and no release notes announced it. Only an address the provider marks as verified is used to match or create an account. OIDC
  • Refused sign-ins say why. When a single sign-on is refused, the login page shows a plain message for the reason, such as an address already held by another account or a domain that is not allowed. The message is chosen from the refusal code, never from text in the address bar.
  • Provider-wrapped addresses are matched. On a first OIDC sign-in, the address is matched by its parsed form, so an address sent as <a@example.com> finds the account for a@example.com instead of creating a second one. The sign-in is refused instead when that account is an administrator, or is already linked to SAML or to another OIDC identity.
  • Identity-provider lockout guard. A SAML or OIDC settings change that would leave no administrator able to sign in is refused. Design notes
  • Signup asks later. The display name and password are chosen when the email is verified. Details
  • Guest submission works. A visitor files a ticket at /submit without an account, receives a per-ticket link, and can reply through it. Attaching a file is possible only through the API. The guest page has no upload control, and that is not available in 1.3.0. Guest access
  • Closed means closed. A closed ticket is read-only and stays closed by default. The way on is a linked follow-up ticket. An operator can allow admins, or staff and admins, to reopen a closed ticket. Follow-up tickets
  • The lifecycle runs itself. An auto-close sweep runs every five minutes. A reopen window of 0 closes a resolved ticket on the next sweep.
  • SLA tracking end to end. Timers pause while a ticket is Pending, a breach sweep runs, and the indicators are colour-coded. The switch is under Admin → Settings.
  • Reporters can attach files to replies. Details
  • Works on a phone. Staff triage and reporters can use the app on a phone. Administration stays on the desktop. Design notes
  • First-run setup creates a category. A new instance can file a ticket straight away. First-run setup
  • A readable audit log. A per-ticket activity feed and an admin-wide searchable view. Audit log
  • Notifications from an outbox. Email is queued in the database and retried after 30 seconds, doubling each time, up to eight attempts. Webhooks are queued too, but each one is sent once and never retried; the Webhooks screen shows each hook's last delivery result.
  • Webhooks with chat formats. An Admin → Webhooks screen, with Slack, Teams, Discord and JIRA payload formats. Webhooks
  • Attachment security. Content detection, mismatch handling, quarantine, download-only files, and optional scanning and reputation lookups. Attachment Security
  • Published images. Multi-architecture images for amd64 and arm64, published to GHCR. Building from source is still supported. Quick start
  • Loud configuration warnings. Example secrets are reported at startup and in a red banner for administrators; "scanning is off" is reported at startup and by GET /api/v1/admin/security-warnings.

ClamAV is opt-in

Docker Compose used to start the bundled ClamAV scanner and set CLAMAV_ADDR for you. From 1.3.0 it is opt-in (#297). An install that relied on that, and whose docker/.env has no CLAMAV_ADDR line, stops scanning attachments on upgrade. Nothing else changes.

Nothing in the admin interface says so: with no scanner address the scan policy is off, and the warning banner only appears when a configured scanner is unreachable. The server logs attachment scanning is OFF: no scanner address is configured at startup (#303), and GET /api/v1/admin/security-warnings reports Attachments are not scanned. Uploads are accepted without being checked. Check Admin → Settings → Attachments → Malware scanning. Nothing stops the upgrade, so check for it. To keep scanning on, uncomment the two lines in the "Virus scanning" section of docker/.env.example in your own docker/.env, then restart:

CLAMAV_ADDR=tcp://clamav:3310
COMPOSE_PROFILES=antivirus

clamav/clamav is published for linux/amd64 only. On Apple Silicon the scanner runs under emulation rather than failing to pull.

Once CLAMAV_ADDR is set, uploads are refused with 503 while the scanner cannot be reached. That covers the first few minutes after the first start, while the scanner downloads its signature database (about 300 MB). Everything other than attachment upload keeps working.

See Getting Started → Virus scanning.

The audit log is readable, and still kept forever

Entries were written before 1.3.0, but nothing could read them. From 1.3.0 there is a per-ticket activity feed and an admin-wide searchable view.

Nothing is deleted unless you ask. audit_retention_days defaults to 0, which keeps everything. To start pruning, set it to a number of days under Admin → Settings. The maximum is 36,525 days, a century. Set it back to 0 to keep everything again. The first sweep runs two minutes after the server starts, then once a day, so an instance that restarts more often than daily still prunes. Only a signed-in administrator can change this setting. An API key cannot, because shortening retention destroys evidence rather than merely widening access.

Staff see the per-ticket feed. The field-level before and after diff is behind a second setting, staff_can_view_ticket_change_history. It is off by default, so no instance starts showing staff something it did not show them in 1.2.0.

A machine credential needs the audit:read scope to read the admin-wide view.

See Admin Guide → Audit log.

Signup asks for the name and password when the email is verified

Before this change, anyone who knew an address could sign up again after its owner, with a password or name of their own. The owner, clicking the newest link, got an account with it. The signup form now asks only for the email address. The link in the email opens a page that asks for the display name and the password.

For API clients:

  • POST /api/v1/auth/verify-email requires token, display_name and password. A request with a missing or invalid name or password is refused with display_name_required, password_too_short or password_too_long, and the link is not used up.
  • A display_name or password sent to POST /api/v1/auth/signup is ignored.
  • GET /api/v1/auth/verify-email?token= returns the email address the link is for.

Signups still pending at upgrade keep working. Their links now ask for a name and a password.

guest_submission_enabled requires a signed-in administrator

This setting decides whether anonymous people can file tickets. It also decides whether the category list can be read without signing in. An API key with settings-write scope could previously switch it either way. Now only a signed-in administrator can change it. An API key cannot, whatever scopes it holds. The refusal is 403 session_required.

A malformed or null value is refused outright, rather than being read back as false.

See the API settings that need a person.

Reporters can attach files to replies

The upload API never checked the role. Any signed-in user who could see a ticket could already attach a file to it. The reply composer offered the control to staff only. A reporting user replying to their own ticket now sees the same Add files control that staff have.

Building from source needs Docker Buildx

Building the image yourself with docker compose -f docker-compose.yml -f docker-compose.build.yml up -d --build needs the docker buildx CLI plugin. Without it, on Apple Silicon and other hosts that are not amd64, the build fails at its first step with a --platform= parse error. A later attempt to work around that produced an image that builds cleanly and does not run, so it was reverted.

Docker Desktop includes Buildx. If docker buildx version fails, install the plugin. The steps are under Building from source in Getting Started.

This only affects building. The quick start pulls a published image, so most people never run a builder at all.

Two environment variables are gone

MFA_ENABLED and GUEST_SUBMISSION_ENABLED were removed in 1.3.0. Nothing read them, so an instance that set them got no error and no change. MFA and guest submission are switched on under Admin → Settings, and that setting is the switch.

SLA_ENABLED still exists. It switches SLA tracking on at each start, and never off. The setting under Admin → Settings is the switch.

No SAML environment variable is read. SAML and OIDC are configured under Admin → Settings → Authentication.

A ticket you cannot see answers 404, not 403

Who notices: API clients that branch on 403.

The REST API used to answer 403 Forbidden for a ticket that exists but that the caller may not see. It now answers 404 Not Found, the same answer a tracking number that does not exist gets. Tracking numbers run in sequence, so a signed-in reporter could walk them to learn which tickets exist. This is a deliberate change to the REST API's published contract. A client that reads 403 as "this ticket exists, but not for you" will now get 404 for the same request.

See REST API → Visibility and tracking numbers.

Closed tickets stay closed for staff and admins

Who notices: staff, administrators, and automation that reopens tickets.

A Closed ticket is now read-only for everyone, staff and administrators included, unless the instance allows reopening. The setting is Reopening closed tickets, under Admin → Settings → General → Ticket lifecycle (closed_reopen_policy). It is off by default. It can allow administrators, or staff and administrators, and it never allows requesters. Until 1.3.0, staff and administrators could reopen a Closed ticket. With the setting off, the status picker, the reopen endpoint (POST /api/v1/tickets/{id}/reopen) and the MCP update_ticket_status tool all refuse to reopen one. The way on is a linked follow-up ticket.

A reopen window of 0 now closes a resolved ticket on the next auto-close sweep, about five minutes after it is resolved.

Uploads wait for the scanner, or are refused

Who notices: installs that set CLAMAV_ADDR, including bare-metal and Kubernetes installs.

Once a scanner address is set, attachment_scan_policy defaults to required. An upload is refused with 503 and a Retry-After header while the scanner cannot be reached. It is not accepted unscanned. Version 1.2.0 accepted uploads without a scan when the scanner was unreachable. To keep that behaviour, choose Scan, but accept uploads while the scanner is down under Admin → Settings → Attachments → Malware scanning. That is a choice you make, not the default.

SVG logos are refused

Who notices: instances whose logo is an SVG file.

The logo accepts PNG, JPG and GIF files, and SVG is refused. The logo is the one uploaded file the application shows inline on its own origin, where staff sessions live, and an SVG file can carry scripts. An SVG logo uploaded by an earlier release is no longer served, so the sidebar falls back to the site name. Upload a PNG, JPG or GIF under Admin → Settings → Branding.

Postgres listens on loopback only in Compose

Who notices: anything that reached the database from another machine, such as a backup job or a reporting tool.

The shipped Compose file publishes Postgres on 127.0.0.1:5432. Version 1.2.0 published it on every interface, and Docker handles a published port before the host firewall sees it, so closing the port in ufw or firewalld did not protect it. After the upgrade, only processes on the Docker host can connect. Run such tools on the host, or reach the database through an SSH tunnel.

Quoted email addresses are refused

Who notices: anyone whose address needs quotation marks, and single sign-on users whose provider sends one.

An address whose local part needs quotation marks, such as "john doe"@example.com, is refused with 400 wherever an address is saved: at signup, on a guest ticket, and when an account is created or edited. Parsing used to drop the quotes, which turned it into an address the mailer could not send to, so the person was never sent their link. Quotation marks that were never needed are dropped and the address kept: "john"@example.com is stored as john@example.com. Addresses already stored are not changed. A first sign-in through SAML or OIDC with an address that needs quotation marks creates no account, and the login page says the address cannot be used (invalid_email). An existing single sign-on user keeps the address they have.

Passwords are limited to 72 bytes

Who notices: anyone who sets a password, and API clients that set one.

A password must be 8 to 72 bytes. The limit is bcrypt's: bcrypt reads only the first 72 bytes and will not hash more. Bytes are counted, not characters, so an accented letter takes two bytes and most other non-Latin characters take three or four. A longer password is refused with a 400 that names the limit. Before 1.3.0, most paths that set a password answered with a server error (500). Sign-in applies no maximum.

Doing the upgrade

  1. Take a database backup. Migrations are forward-only; there is no automatic rollback.
  2. If you scan attachments with the bundled ClamAV, add the two lines to docker/.env. See ClamAV is opt-in.
  3. Update and restart. 
    cd go-help-desk
git pull
cd docker
docker compose pull
docker compose up -d
    If you checked out a tag earlier (for example v1.2.0), run git checkout main before git pull. If you build from source, run the build command from Building from source instead of the two docker compose commands. Migrations run automatically on startup, before the server accepts traffic.
  4. Sign in as an administrator. Look for the red insecure-configuration banner, and check the scanning setup under Admin → Settings → Attachments → Malware scanning. Decide audit_retention_days and whether staff should see the field-level change history (staff_can_view_ticket_change_history).
  5. If you have API clients that drive signup, update them for the new verification request.

For the general mechanics, including zero-downtime upgrades, see Getting Started → Upgrading.
