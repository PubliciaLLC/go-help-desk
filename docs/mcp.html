MCP Server

Give AI assistants native access to your help desk using the Model Context Protocol.

Go Help Desk includes a built-in Model Context Protocol (MCP) server at /mcp. MCP lets an AI assistant call help desk operations as structured tools rather than driving the web UI.

With the MCP server connected, an AI assistant can:

  • List and search the tickets the caller can see, and read one with its replies and links
  • Look up the category catalogue and the statuses this instance defines
  • Open a ticket, on the caller's behalf or someone else's
  • Add a reply or an internal note
  • Assign or unassign a ticket, change its status, and open a follow-up from a closed ticket

The tools call the same ticket service as the REST API and use the same visibility rule, so an assistant using an account's credentials sees and changes only what that account could through the API.

Available tools

Eleven tools. Six read and five write. Identifiers are UUIDs, except that get_ticket and list_attachments also take a tracking number. A tool that fails answers with an MCP tool error, a plain sentence the assistant can show its user.

get_ticket

Get one ticket by UUID or tracking number, with its replies and linked tickets.

ParameterTypeDescription
idstring (required)Ticket UUID, or a tracking number such as GHD-2026-000001.
include_repliesboolean (optional)Include the reply thread and the ticket's links. Default true.

A reporting user never receives internal notes. A ticket the caller may not see is answered with the same "not found" message as one that does not exist. For staff and administrators the ticket carries source_channel, how it arrived (web, api, mcp, guest or phone); a reporting user never receives it.

list_tickets

List the tickets the caller can see, with optional filters.

ParameterTypeDescription
assignee_user_idstring (optional)Only tickets assigned to this user.
status_idstring (optional)Only tickets in this status (see list_statuses).
prioritystring or array of strings (optional)critical, high, medium or low: one value, or an array of at most 20 to match any of them.
category_idstring (optional)Only tickets in this category (see list_categories).
qstring (optional)Full-text search over subject, description and tracking number.
search_repliesboolean (optional)With q, also match the replies. A ticket matches when one reply holds every word. Default false. New in 1.3.0
scopestring (optional)Which queue: mine, assigned_to_me, my_groups, unassigned, all or visible. Absent or null means visible, which is what this tool has always listed. An unknown value, an empty string or a value that is not a string is refused ("invalid scope"). New in 1.3.0 See Queues over MCP.
held_bystring (optional)nobody, me or others: no person holds the ticket, the caller holds it, or someone else does. Any other value is refused ("invalid held_by"). Staff and administrators only. New in 1.3.0
awaiting_replyboolean (optional)true keeps the tickets that are not Resolved or Closed and whose newest public message is from the requester's side, so they are waiting for the help desk. A value that is not a boolean, such as the string "true", is refused ("invalid awaiting_reply"). Staff and administrators only. New in 1.3.0
assignee_group_idstring (optional)Only tickets assigned to this group. Staff and administrators only.
status_idsarray of strings (optional)Only tickets in any of these statuses, at most 20. May be combined with status_id. New in 1.3.0
include_closedboolean (optional)false leaves out Closed tickets. Ignored when a status is named. Default true. New in 1.3.0
type_id, item_idstring (optional)Only tickets of this type, or of this item. New in 1.3.0
reporter_idstring (optional)Only tickets this account reported. Staff and administrators only. New in 1.3.0
requesterstring (optional)Free text, 2 to 254 characters. Staff and administrators only. An API key or OAuth client needs requester_search:read. See Free-text requester search. New in 1.3.0
created_after, created_beforestring (optional)RFC 3339 times. New in 1.3.0
updated_after, updated_beforestring (optional)RFC 3339 times. Staff and administrators only. New in 1.3.0
source_channelarray of strings (optional)Any of web, api, mcp, guest or phone. Staff and administrators only. New in 1.3.0
slastring (optional)breached or at_risk. Refused while SLA tracking is off. Staff and administrators only. New in 1.3.0
sort, orderstring (optional)sort is number, subject, status, priority, sla, created or updated; order is asc or desc. sla is refused while SLA tracking is off, and a reporting user may not sort by updated or sla. The other rules are those of REST, see Searching tickets over the REST API. New in 1.3.0
limitnumber (optional)1 to 100, default 20. A larger value is clamped to 100.
offsetnumber (optional)Pagination offset.

The filters narrow what the caller can already see. They never widen it: a reporting user lists only their own tickets whatever the arguments say.

Queues over MCP New in 1.3.0

  • scope takes the same six values as scope on GET /api/v1/tickets, with the same permission rules and the same refusals in the same words: unassigned is for administrators, and for staff only while an administrator has ticked Staff under Admin → System → Privacy → Available queue, and all is for administrators only. Otherwise the answer is "only admins can use this scope". See Queues over REST for what each value returns.
  • A call that sends no scope returns what it always did, every ticket the caller can see. The queues never widen what the caller may see.
  • held_by and awaiting_reply are refused for a reporting user, as over REST ("held_by is not available to requesters", "awaiting_reply is not available to requesters").
  • There is no tool for the dashboard or for reports. GET /api/v1/dashboard and GET /api/v1/reports/kpi are REST only (see Dashboard and reports).

Searching replies New in 1.3.0

  • search_replies is off unless the call asks for it, so a call without it returns the tickets it always did. The ticket list page has it on by default. MCP does not.
  • A ticket found through a reply carries a reply_match object: reply_id, internal, created_at and snippet. The key is absent on any other ticket. The snippet is the reply's own text with each matched word wrapped in the control characters U+0002 and U+0003, not HTML. It never names an author.
  • Internal notes are searched for staff and administrators only. A reporting user searches public replies and never receives an excerpt of an internal note. The server decides this from the caller's role. No argument can change it, and an include_internal argument is ignored.
  • If the replies could not be searched, the answer carries a second text block after the list, and the list is still a plain JSON array. It says either that reply search is still being prepared after an upgrade, or that the search took too long. The tickets listed then match on subject, description or number only. See the limits on reply search.
  • Only the first 50,000 characters of a reply are searched.

Free-text requester search

requester works as it does over REST: free text, 2 to 254 characters, matched against the reporter's name or email and a guest's name or email. Staff and administrators only. An API key or OAuth client needs the requester_search:read scope for it; without the scope the call is refused. reporter_id does not need it. See Searching tickets over the REST API.

list_attachments New in 1.3.0

List the files attached to a ticket. Metadata only: no file content is returned, and no reputation lookup is made.

ParameterTypeDescription
ticket_idstring (required)Ticket UUID, or a tracking number such as GHD-2026-000001.

Each file has id, filename, mime_type, size_bytes, created_at, detected_mime, sha256, virus_name, mismatch and quarantined. quarantined is true when the scanner identified the file as malicious, and virus_name says what it found. mismatch is true when the content contradicts the file's name, and null when the file was never inspected. Attachments are download-only in the web interface, and there is no tool that returns their content. A ticket the caller may not see is answered with the same "not found" message as one that does not exist.

list_categories

The Category, Type and Item catalogue, as a tree, for composing create_ticket.

ParameterTypeDescription
include_inactiveboolean (optional)Include retired entries. Default false.

list_statuses

The ticket statuses this instance defines, with their IDs, for list_tickets and update_ticket_status. No parameters.

list_ticket_fields New in 1.3.0

List the custom fields the new-ticket form shows for a category, and for a type and item under it: the fields create_ticket takes in custom_fields.

ParameterTypeDescription
category_idstring (required)Category UUID (see list_categories).
type_idstring (optional)Type UUID, to include the fields attached to the type.
item_idstring (optional)Item UUID, to include the fields attached to the item.

Each field has an id, a name, a field_type (text, textarea, number or select), its options for a select, whether it is required, its max_length and the level it is attached at. Only fields that are active and shown on the new-ticket form are listed.

create_ticket

Open a new ticket.

ParameterTypeDescription
subjectstring (required)Short summary.
category_idstring (required)Category UUID.
type_idstring (optional)Type UUID. Must belong to the category.
item_idstring (optional)Item UUID. Must belong to the type.
descriptionstring (optional)Full description, written as Markdown unless format is plain. Escape characters you mean literally (*, #, _).
formatstring (optional)markdown (the default) or plain. Anything else is a tool error and nothing is written.
prioritystring (optional)critical, high, medium or low. Default medium.
reporter_user_idstring (optional)Who the ticket is for, as an account id. Defaults to the authenticated caller. Not with reporter_email.
reporter_emailstring (optional)Who the ticket is for, as an address. The ticket is filed for the account with that address if there is one, otherwise it is a guest ticket and the guest link is emailed. Not with reporter_user_id.
guest_namestringRequired whenever reporter_email is given, whether or not the address has an account.
guest_phonestring (optional)Kept with a guest ticket.
custom_fieldsobject (optional)Custom field values: an object of field id to a string value, with the ids and options from list_ticket_fields. A value that is not a string, or an argument that is not an object, is a tool error. New in 1.3.0 See Custom fields over MCP.

A ticket made here is recorded as arriving by MCP, including one filed for someone else. A source_channel argument is a tool error and nothing is written. A malformed type_id, item_id or reporter_user_id is refused rather than ignored. reporter_user_id files the ticket for that user: you, the caller, are recorded as the one who filed it (earlier, the reporter was recorded as the actor), and the user is emailed the usual "We have received your ticket" message, as through the REST API. The same holds for reporter_email, by the same rules as the REST API: an account if the address has one, otherwise a guest ticket (refused while guest submission is off), and every use of reporter_email costs one of 40 an hour per staff member, shared with REST, which is never given back. Creating your own ticket is unchanged. Two things differ from creating a ticket through the REST API: a ticket opened here is not auto-assigned, and custom field values cannot be set.

Custom fields over MCP New in 1.3.0

  • A field the ticket's classification requires must have a value. Without one the ticket is refused and nothing is created.
  • For any other field, a value that is not accepted (an unknown or inactive field, a retired or unlisted option, a number that is not a number) is dropped, and the result lists it under warnings as {"field_id", "reason"}. The key is absent when nothing was dropped. An empty value means no value and is not a warning.
  • get_ticket returns the ticket's custom_fields to staff and administrators, never to a reporting user.

add_reply

Add a reply or an internal note to a ticket, authored by the authenticated caller.

ParameterTypeDescription
ticket_idstring (required)Ticket UUID.
bodystring (required)Reply body, written as Markdown unless format is plain. Escape characters you mean literally. At most 50,000 bytes; longer is a tool error.
formatstring (optional)markdown (the default) or plain.
internalboolean (optional)An internal note, never shown to the requester. Default false.

A public reply emails the requester, the same as a reply through the REST API: the guest's address (with a link to the ticket) or the reporting account's address. An internal note sends nothing. There is no notify_customer switch over MCP, so use an internal note for anything that should not reach the requester. A staff member or administrator replying publicly on a ticket they filed themselves is not sent a copy of their own reply. Either kind of reply raises the ticket.replied event, so webhooks receive it. Anything connected over MCP with tickets:write can therefore send mail to your customers.

assign_ticket

Assign a ticket to a user or a group, or take it off whoever has it, as the authenticated caller.

ParameterTypeDescription
ticket_idstring (required)Ticket UUID.
assignee_user_idstring (optional)User UUID to assign to.
assignee_group_idstring (optional)Group UUID to assign to.
clear_assigneeboolean (optional)Take the ticket off whoever has it.

Give an assignee ID, or clear_assignee: true. Omitting both is refused, and so is combining clear_assignee with an ID. An ID that is empty, null, not a string or not a valid UUID is refused rather than read as "nobody", so a mistake never quietly takes a ticket off the person working it.

update_ticket_status

Move a ticket to another status.

ParameterTypeDescription
ticket_idstring (required)Ticket UUID.
status_idstring (required)Target status UUID (see list_statuses).

The same rules as a status change anywhere else apply. Only an administrator can move a ticket to Closed. Moving a ticket out of Closed is refused unless Reopening closed tickets allows the caller's role, and the refusal says why. To continue the work on a closed ticket, use create_follow_up.

create_follow_up

Open a new ticket that continues a closed one, linked back to it.

ParameterTypeDescription
ticket_idstring (required)UUID of the closed ticket to continue.

It copies the subject, description, category, type, item, priority, requester and the custom field values whose fields still apply (a value a field no longer accepts is left out), not the replies, attachments or history. The values are copied after the follow-up is filed: if that fails, the follow-up stands without them. It works only on a Closed ticket. Staff and administrators can open as many follow-ups from one closed ticket as they need; only a requester is limited to one. See Follow-up tickets.

Connecting clients

The server speaks two transports. The current one, Streamable HTTP, is at:

<BASE_URL>/mcp

It is stateless: each request is a POST that carries one complete JSON-RPC message and is answered with application/json. There is no session id, and GET and DELETE answer 405. /mcp/ answers the same as /mcp.

The older HTTP with Server-Sent Events (SSE) transport is kept so existing configurations keep working. A client opens the event stream at:

<BASE_URL>/mcp/sse

and the server tells it where to post messages (/mcp/message). The examples below use the SSE URL. Whichever you choose, send an Authorization header with every request (see Authentication).

Requests from another origin are refused. Every MCP route answers 403 with the code origin_not_allowed when the request carries an Origin header that is not the origin of your BASE_URL. This is checked before authentication. A request with no Origin header, which is what SDKs, editors and curl send, is not affected. A browser-based client has to be served from the BASE_URL origin, and a reverse proxy must not add an Origin header.

Claude Code

claude mcp add --transport sse helpdesk \
  https://helpdesk.example.com/mcp/sse \
  --header "Authorization: ApiKey GHD_3f8a…"

To share the server with a project instead, put it in .mcp.json at the project root:

{
  "mcpServers": {
    "helpdesk": {
      "type": "sse",
      "url": "https://helpdesk.example.com/mcp/sse",
      "headers": {
        "Authorization": "ApiKey GHD_3f8a…"
      }
    }
  }
}

VS Code

VS Code has native MCP support. Add the server to .vscode/mcp.json in your workspace (or to your user profile's mcp.json):

{
  "servers": {
    "helpdesk": {
      "type": "sse",
      "url": "https://helpdesk.example.com/mcp/sse",
      "headers": {
        "Authorization": "ApiKey GHD_3f8a…"
      }
    }
  }
}

Format taken from VS Code's MCP configuration reference: top-level servers, type of http or sse, plus url and headers.

Continue

Continue reads MCP servers from YAML files in a .continue/mcpServers/ folder at the top of your workspace, for example .continue/mcpServers/helpdesk.yaml:

name: Go Help Desk
version: 0.0.1
schema: v1
mcpServers:
  - name: helpdesk
    type: sse
    url: https://helpdesk.example.com/mcp/sse
    requestOptions:
      headers:
        Authorization: ApiKey GHD_3f8a…

Format taken from Continue's MCP deep dive (file location, type: sse, url) and its config reference, which gives MCP servers an optional requestOptions for sse and streamable-http servers, in the same format as a model's requestOptions, where headers sets custom request headers. Neither page shows a remote server with a header, so this snippet puts the two together rather than copying a worked example.

Cursor

Add the server to .cursor/mcp.json in your project, or to ~/.cursor/mcp.json to make it available everywhere:

{
  "mcpServers": {
    "helpdesk": {
      "url": "https://helpdesk.example.com/mcp/sse",
      "headers": {
        "Authorization": "ApiKey GHD_3f8a…"
      }
    }
  }
}

Format taken from Cursor's Model Context Protocol documentation: a remote server entry takes url and optional headers, and its remote examples carry no type key.

Other clients

Any MCP client that supports the SSE transport and custom request headers works. Give it the /mcp/sse URL and the Authorization header. A client that supports the Streamable HTTP transport can use /mcp instead.

Authentication

Every published MCP advisory is fixed in v1.2.0, and only the 1.3 line receives security fixes. Up to and including v1.1.0 the MCP server required no authentication at all (GHSA-5g72-m483-3v63, GHSA-26xr-728v-639v). Up to and including v1.1.1 it still exposed every ticket (GHSA-2x4f-j4jv-m2cm) and did not check scopes (GHSA-p2wx-wvfr-7h3p). See Security.

The MCP server sits behind the same authentication as the REST API and accepts any of:

  • API key: Authorization: ApiKey <token>. The token is GHD_ followed by 64 hex characters, shown once when the key is created (by an administrator, or by a staff member for their own key when that is allowed), under Admin → Integrations → API Keys or Account → API keys.
  • OAuth2 access token: get one from POST /api/v1/auth/oauth/token with client credentials, and send it as Authorization: Bearer <token>.
  • Session cookie: works, but is only useful from a browser.

A request with no valid credential gets 401. A signed-in session that has not passed its second factor gets 403, so MCP cannot be used to skip an MFA challenge. API keys and OAuth tokens do not go through MFA.

One credential per integration. Create a dedicated API key for each assistant or integration, with only the scopes it needs: tickets:read for the read tools, plus tickets:write to let it change tickets. Revoking one then leaves the others working.

Request size and sessions

  • A request body is capped at 1 MiB on /mcp, /mcp/ and /mcp/message. A larger one is refused with 413 and the code request_too_large, on both transports. A declared Content-Length over the limit is refused before any of the body is read. Nothing in normal use comes near it: ticket descriptions are already capped at 50,000 bytes.
  • An SSE session belongs to whoever opened the stream. A message posted to /mcp/message for it by anyone else, by a different API key of the same user, or by a browser session when the stream was opened with a key (or the reverse), is refused with 403 and not processed. A missing, unknown or closed sessionId gets the same 403, and the answer is the same in every case, so it does not reveal which sessions exist. A client that opens the stream and posts with the same credential, which is every ordinary MCP client, is unaffected. Streamable HTTP at /mcp keeps no session.

Permissions

Every signed-in role can connect. What a caller may then do is decided per tool:

  • Reads are filtered by the same visibility rule as the REST API. A reporting user sees only their own tickets and never internal notes. Staff see what their ticket visibility allows, which is every ticket unless Limit staff to their group scope is on. Administrators see everything.
  • Writes need a Staff or Admin account. A reporting user who calls one gets a tool error saying so.
  • Machine credentials also need the scope in the table above. An API key or OAuth client without it gets a tool error naming the missing scope.
  • An OAuth client acts as its service user. A client holding tickets:write can use the write tools as that user, and what it does is recorded under the client's name. The service user is staff unless an administrator changed it to the user role, and a user-role account cannot write. An API key acts as the administrator who created it.

A ticket the caller may not see is reported exactly as one that does not exist, so the tools cannot be used to find out which tracking numbers are real.

Identity comes from the request, never from a tool argument. An earlier version accepted author_user_id and actor_user_id parameters, so a caller named itself and the server believed it. Those parameters no longer exist. The one identity field that remains, reporter_user_id on create_ticket, names the subject of a ticket rather than the caller, because staff legitimately open tickets on someone's behalf.

Ticket rules are the ticket service's own, not a second copy: an MCP status change, follow-up or reply is refused in exactly the cases the same action through the REST API is.
