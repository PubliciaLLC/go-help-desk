MCP Server

Give AI assistants native access to your help desk using the Model Context Protocol.

Go Help Desk includes a built-in Model Context Protocol (MCP) server under /mcp/. MCP lets an AI assistant call help desk operations as structured tools rather than driving the web UI.

With the MCP server connected, an AI assistant can:

  • List and search the tickets the caller can see, and read one with its replies and links
  • Look up the category catalogue and the statuses this instance defines
  • Open a ticket, on the caller's behalf or someone else's
  • Add a reply or an internal note
  • Assign or unassign a ticket, change its status, and open a follow-up from a closed ticket

The tools call the same ticket service as the REST API and use the same visibility rule, so an assistant using an account's credentials sees and changes only what that account could through the API.

Available tools

Nine tools. Four read and five write. Identifiers are UUIDs, except that get_ticket also takes a tracking number. A tool that fails answers with an MCP tool error, a plain sentence the assistant can show its user.

get_ticket

Get one ticket by UUID or tracking number, with its replies and linked tickets.

ParameterTypeDescription
idstring (required)Ticket UUID, or a tracking number such as GHD-2026-000001.
include_repliesboolean (optional)Include the reply thread and the ticket's links. Default true.

A reporting user never receives internal notes. A ticket the caller may not see is answered with the same "not found" message as one that does not exist.

list_tickets

List the tickets the caller can see, with optional filters.

ParameterTypeDescription
assignee_user_idstring (optional)Only tickets assigned to this user.
status_idstring (optional)Only tickets in this status (see list_statuses).
prioritystring (optional)critical, high, medium or low.
category_idstring (optional)Only tickets in this category (see list_categories).
qstring (optional)Full-text search over subject, description and tracking number.
limitnumber (optional)1 to 100, default 20. A larger value is clamped to 100.
offsetnumber (optional)Pagination offset.

The filters narrow what the caller can already see. They never widen it: a reporting user lists only their own tickets whatever the arguments say.

list_categories

The Category, Type and Item catalogue, as a tree, for composing create_ticket.

ParameterTypeDescription
include_inactiveboolean (optional)Include retired entries. Default false.

list_statuses

The ticket statuses this instance defines, with their IDs, for list_tickets and update_ticket_status. No parameters.

create_ticket

Open a new ticket.

ParameterTypeDescription
subjectstring (required)Short summary.
category_idstring (required)Category UUID.
type_idstring (optional)Type UUID. Must belong to the category.
item_idstring (optional)Item UUID. Must belong to the type.
descriptionstring (optional)Full description.
prioritystring (optional)critical, high, medium or low. Default medium.
reporter_user_idstring (optional)Who the ticket is for. Defaults to the authenticated caller.

A malformed type_id, item_id or reporter_user_id is refused rather than ignored. Two things differ from creating a ticket through the REST API: a ticket opened here is not auto-assigned, and custom field values cannot be set.

add_reply

Add a reply or an internal note to a ticket, authored by the authenticated caller.

ParameterTypeDescription
ticket_idstring (required)Ticket UUID.
bodystring (required)Reply body.
internalboolean (optional)An internal note, never shown to the requester. Default false.

A reply added through MCP sends no notification email: the tool does not look up the requester's address. It does raise the ticket.replied event, so webhooks receive it.

assign_ticket

Assign a ticket to a user or a group, or take it off whoever has it, as the authenticated caller.

ParameterTypeDescription
ticket_idstring (required)Ticket UUID.
assignee_user_idstring (optional)User UUID to assign to.
assignee_group_idstring (optional)Group UUID to assign to.
clear_assigneeboolean (optional)Take the ticket off whoever has it.

Give an assignee ID, or clear_assignee: true. Omitting both is refused, and so is combining clear_assignee with an ID. An ID that is empty, null, not a string or not a valid UUID is refused rather than read as "nobody", so a mistake never quietly takes a ticket off the person working it.

update_ticket_status

Move a ticket to another status.

ParameterTypeDescription
ticket_idstring (required)Ticket UUID.
status_idstring (required)Target status UUID (see list_statuses).

The same rules as a status change anywhere else apply. Only an administrator can move a ticket to Closed. Moving a ticket out of Closed is refused unless Reopening closed tickets allows the caller's role, and the refusal says why. To continue the work on a closed ticket, use create_follow_up.

create_follow_up

Open a new ticket that continues a closed one, linked back to it.

ParameterTypeDescription
ticket_idstring (required)UUID of the closed ticket to continue.

It copies the subject, description, category, type, item, priority and requester, not the replies, attachments, history or custom fields. It works only on a Closed ticket. Staff and administrators can open as many follow-ups from one closed ticket as they need; only a requester is limited to one. See Follow-up tickets.

Connecting clients

The server uses MCP's HTTP with Server-Sent Events (SSE) transport. A client opens the event stream at:

<BASE_URL>/mcp/sse

and the server tells it where to post messages (/mcp/message). Nothing else under /mcp/ answers. Configure your client for an SSE server at that URL, and send an Authorization header with every request (see Authentication).

Claude Code

claude mcp add --transport sse helpdesk \
  https://helpdesk.example.com/mcp/sse \
  --header "Authorization: ApiKey GHD_3f8a…"

Other clients

Any MCP client that supports the SSE transport and custom request headers works. Give it the /mcp/sse URL and the Authorization header. A client configured for the newer Streamable HTTP transport against /mcp/ will not connect.

Authentication

Every published MCP advisory is fixed in v1.2.0, and only the 1.3 line receives security fixes. Up to and including v1.1.0 the MCP server required no authentication at all (GHSA-5g72-m483-3v63, GHSA-26xr-728v-639v). Up to and including v1.1.1 it still exposed every ticket (GHSA-2x4f-j4jv-m2cm) and did not check scopes (GHSA-p2wx-wvfr-7h3p). See Security.

The MCP server sits behind the same authentication as the REST API and accepts any of:

  • API key: Authorization: ApiKey <token>. The token is GHD_ followed by 64 hex characters, shown once when an administrator creates the key under Admin → API Keys.
  • OAuth2 access token: get one from POST /api/v1/auth/oauth/token with client credentials, and send it as Authorization: Bearer <token>.
  • Session cookie: works, but is only useful from a browser.

A request with no valid credential gets 401. A signed-in session that has not passed its second factor gets 403, so MCP cannot be used to skip an MFA challenge. API keys and OAuth tokens do not go through MFA.

One credential per integration. Create a dedicated API key for each assistant or integration, with only the scopes it needs: tickets:read for the read tools, plus tickets:write to let it change tickets. Revoking one then leaves the others working.

Permissions

Every signed-in role can connect. What a caller may then do is decided per tool:

  • Reads are filtered by the same visibility rule as the REST API. A reporting user sees only their own tickets and never internal notes. Staff see what their ticket visibility allows, which is every ticket unless Limit staff to their group scope is on. Administrators see everything.
  • Writes need a Staff or Admin account. A reporting user who calls one gets a tool error saying so.
  • Machine credentials also need the scope in the table above. An API key or OAuth client without it gets a tool error naming the missing scope.
  • An OAuth client can read but not write. It has no user identity, and every write records which user acted, so the write tools refuse it. Use an API key, which acts as the administrator who created it, to write.

A ticket the caller may not see is reported exactly as one that does not exist, so the tools cannot be used to find out which tracking numbers are real.

Identity comes from the request, never from a tool argument. An earlier version accepted author_user_id and actor_user_id parameters, so a caller named itself and the server believed it. Those parameters no longer exist. The one identity field that remains, reporter_user_id on create_ticket, names the subject of a ticket rather than the caller, because staff legitimately open tickets on someone's behalf.

Ticket rules are the ticket service's own, not a second copy: an MCP status change, follow-up or reply is refused in exactly the cases the same action through the REST API is.
