Security

Every security issue we have found or been told about is published as a GitHub advisory, with the versions it affects and the release that fixes it. This page lists them, says how to report one, and points at the deeper writeups.

Run 1.3.0. Every advisory below is fixed in v1.2.0, but only the 1.3 line receives security fixes. From 1.2, read Upgrading to 1.3.0. From 1.1.1 or earlier, read Upgrading to 1.2.0 first: credentials created in the 1.1.1 admin UI stop working, and everyone is signed out once.

Advisories

Newest first. Severity is ours, assigned with GitHub's CVSS calculator.

Medium

Cross-site request forgery on the MCP routes

GHSA-3jmq-7vm4-cc7p · affects 1.1.1 to 1.2.x · published with the 1.3.0 release

The MCP message route accepted cross-origin requests that carried a session cookie, so a web page on a sibling site could act through a signed-in user's session. From 1.3.0 every MCP route refuses a request whose Origin header is not the origin of BASE_URL.

Fixed in v1.3.0 · Read the advisory →
Critical

Authentication and authorization bypasses

GHSA-p2wx-wvfr-7h3p · affects ≤ 1.1.1 · published 15 Sep 2026

Eight defects in one advisory. MFA could be defeated with a password alone; signed-in users could read and write tickets they had no access to; API key and OAuth scopes were never enforced, so any credential acted with full authority; no credential could be revoked; and any signed-in user could stop the server.

Fixed in v1.2.0 · Read the advisory →
Medium

A regular user could read and post any ticket's replies

GHSA-q9g5-2fp5-hmmx · affects ≤ 1.1.0 · published 15 Sep 2026

Broken function-level authorization: handleListReplies and handleAddReply omitted the ownership check their sibling handlers enforced, so any signed-in user could read any ticket's replies — including internal staff-only notes — and post replies to other people's tickets.

Fixed in v1.1.1 · Read the advisory →
Critical

Unauthenticated MCP ticket access via /mcp/

GHSA-5g72-m483-3v63 · affects 1.0.1 · published 15 Sep 2026

The MCP endpoint served ticket reads and modifications with no authentication at all.

Fixed in v1.1.0 · Read the advisory →
Critical

MCP server allowed impersonated replies and assignment hijack

GHSA-26xr-728v-639v · affects ≤ 1.1.0 · published 13 Sep 2026

With no authentication on the MCP server, anyone who could reach it could read tickets, post replies as somebody else, and reassign work.

Fixed in v1.1.1 · Read the advisory →
Critical

MCP server exposed unauthenticated read and write to all tickets

GHSA-2x4f-j4jv-m2cm · affects ≤ 1.1.1 · published 12 Sep 2026

The same class of exposure as the two above, covering every ticket in the instance.

Fixed in v1.2.0 · Read the advisory →

Reporting a vulnerability

Please do not open a public issue. Report privately through GitHub:

Report a vulnerability privately →

Include as much as you can: what the vulnerability is and what it lets somebody do, how to reproduce it, the affected versions, how the instance is deployed, and any fix you would suggest.

Supported versions

Security fixes are issued for the 1.3 release line only: 1.3.0 and its patch releases. Earlier versions, 1.2 included, are not backported. Two advisories reach back into 1.2, both fixed in 1.3.0: cross-site request forgery on the MCP routes, GHSA-3jmq-7vm4-cc7p (1.1.1 to 1.2.x), and an API key able to revoke another administrator's key (1.0.0 to 1.2.0), published with 1.3.0. Apart from those two, no published advisory affects 1.2.0, and 1.2 receives no further fixes once 1.3.0 ships. Below 1.2 is not merely unsupported: every published advisory affects at least one of those versions, four of them rated critical. 1.3.0 also carries hardening that 1.2 lacks; see the upgrade page. How ticket text is displayed

Anyone who can file a ticket chooses the text staff read, so formatted ticket text (Markdown) is displayed under strict rules. The guarantee is how the page is built, not filtering: every element is created by the application from its own fixed list, all user text is shown as text, and the only attributes that carry user data are a link address, checked against an allowed list, and the start number of a numbered list. A second, independent check runs last, and the content security policy is a third line of defence.

  • No raw HTML and no images. HTML is shown as text. An image is shown as a link, "[image: alt]", and is never loaded, so a ticket cannot be used as a tracking pixel.
  • Links are only http, https and mailto; relative links, javascript:, data:, vbscript: and tel: are plain text. They open in a new tab with noopener noreferrer nofollow ugc, and the real host is shown after the link unless the link text is exactly the address. A look-alike international domain shows in its xn-- form, and invisible and direction-changing characters are removed from link text and host.
  • Two kinds of link are not links. A mailto link with a query (bcc, cc, subject and body can add recipients or write the message) and a link to this help desk's own attachment routes, which would skip the content and reputation warnings of the attachments list.
  • Bounded work. A hostile post cannot slow a page down, because formatting has limits. Text over 50,000 characters is never formatted. A post's tables are limited to 5,000 cells in total. The formatted result is capped at 40,000 pieces (paragraphs, links, table cells and so on). Text with an extreme number of emphasis marks such as * and _ (over 4,000), of open square brackets (over 3,000), or with nesting deeper than 20 levels is refused as too complex. Everything else is formatted in the background with a one-second time limit. Past any of these the post is shown as plain text with a note. Replies are limited to 50,000 bytes when written, and an older, longer post is shown collapsed to its first 5,000 characters until the reader asks for the whole text. A page has an overall budget of formatted text.
  • Every formatted post has a Plain text button that shows the stored characters, so a suspicious link can be checked.
