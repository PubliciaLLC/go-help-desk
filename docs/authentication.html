Authentication

Local accounts, a second factor by authenticator app or passkey, SAML 2.0 and OIDC sign-in, guest links, and API credentials.

Go Help Desk signs people in with a local password, or through an identity provider over SAML 2.0 or OpenID Connect. A password sign-in can require a second factor: an authenticator app (TOTP) or a passkey. Scripts and integrations use API keys or OAuth2 client credentials, and a guest reaches their one ticket through a private link.

Every switch in the table below is an administrator setting under Admin → Settings → Authentication (or General, for guest submission), stored in the database and applied without a restart. None of them is an environment variable, and none can be changed by an API key or OAuth client: they need a signed-in administrator.

MethodWho it's forDefault
Local accountsAll rolesOn
Second factor (TOTP or passkey)Password sign-ins, all rolesOff: Multi-factor authentication → Enable MFA
SAML 2.0All rolesOff: SAML → Enable SAML login
OIDCAll rolesOff: OIDC / OpenID Connect → Enable OIDC login
Self-service signupNew reporting usersOff: Registration → Allow self-service signup
Guest linksPeople without an accountOff: General → Submissions → Guest submission
API keys and OAuth clientsScripts and integrationsKeys: administrators, and staff for their own keys when allowed. OAuth clients: administrators

Local accounts

Users sign in with their email address and password. Passwords are hashed with bcrypt at cost 12. Releases up to 1.2 hashed at cost 10. An older hash keeps working, and is replaced by a cost-12 hash the next time its owner signs in with the password. Each cost step doubles the work, so checking a password now takes about four times as much server time as at cost 10.

Old password hashes expire

An older hash does not keep working forever. Once a set number of days has passed since 1.3.0 first started on your database, a correct password that is still stored in the old form is refused with 403 password_reset_required and the message that it was saved in an older, weaker form and must be reset. The number of days is Admin → Settings → Authentication → Passwords → Reset window for old passwords: 30 by default, from 1 to 365, and changing it moves the deadline for everyone. Anyone who signs in before the deadline is upgraded automatically.

  • Administrators are exempt, so the instance cannot lock itself out. They are upgraded at their next sign-in like everyone else.
  • Staff and users past the deadline are mailed a reset link by the refused sign-in itself when the server can send email (the message says to check email, and Forgot password? on the sign-in page sends another; see Forgot password). If no link could be sent (for example because the account's stored address cannot be mailed, see Addresses must be ASCII) the message says "We could not send a reset link just now. Try again in a minute, or ask an administrator." An administrator can always set a new password under Admin → Users → [user] → Reset password, and with email off that is the only route.
  • People who sign in rarely, such as seasonal staff, are the ones affected. New installs are not.
  • When SAML restricts password sign-in to administrators, other accounts get the SAML refusal instead.

Forgot password

When the server can send email (SMTP_HOST and SMTP_FROM are set), the sign-in page shows a Forgot password? link. The person enters their address and is mailed a link to choose a new password.

  • The answer is always the same. The page says "If that address has an account, we have emailed it a link to choose a new password", whether or not the address has an account, so it does not reveal who has one (POST /api/v1/auth/forgot-password always answers 202).
  • The link works once and for 30 minutes. A newer request replaces the older link. An account is mailed at most once every five minutes, however many requests arrive. A link is built from BASE_URL, never from the request, so make sure BASE_URL is the address people use.
  • Choosing a new password ends every session of that account, so anyone holding an old session is signed out. A pending must choose a new password state (see the unlock command) is cleared. The link does not sign anyone in. The person goes back to the sign-in page and signs in with the new password and their second factor, if they have one. Their API keys are not touched.
  • Who gets a link. Nothing is mailed to a disabled or deleted account, to an account with no password (an account that signs in only through SSO, or a local account created without one), or, when SAML limits password sign-in to administrators, to anyone who is not an administrator.
  • Without email the link is not shown, and the request answers 503 email_not_configured. An administrator setting a password directly still works. GET /api/v1/auth/providers reports password_reset, true when the link is offered.
  • A password outside 8 to 72 bytes is refused with 400, and a link that is wrong, expired or already used with 422 token_invalid. Each reset is recorded in the audit log as password_reset_by_email, with no actor. Both requests count against AUTH_RATE_LIMIT_PER_MINUTE for the client address.

Account creation

Accounts are created in one of four ways:

  • Admin-created: an administrator clicks Add User under Admin → Users and assigns any role.
  • Self-service signup: only when Allow self-service signup is on, which it is not by default. Signup is limited to the Allowed email domains (judged by the domain of the address as it will be stored, so <a@x.com> and A@X.COM both count as x.com) unless Allow open registration is on. A signup page at /signup asks only for an email address and sends a verification link, valid for 24 hours. The display name and password are chosen when the link is opened. A self-registered account gets the User role. Email must be configured, or no link is sent.
  • Signup addresses must be ASCII, and so must each allowed domain (use the xn-- form for an internationalised domain); see Addresses must be ASCII.
  • SAML or OIDC: an account is created at the first sign-in through the identity provider. See SAML 2.0 and OIDC.
  • First-run setup: the first administrator, created at /setup on an empty database.

Password requirements

A password must be at least 8 characters and at most 72 bytes. There is no other complexity rule. Users change their own password on the Your account page, which asks for the current password first; a wrong one is shown inline and the person stays signed in. Through the API, PATCH /api/v1/me/password needs current_password and new_password (the old field name password is still read for the new one) and refuses a missing or wrong current password with 400 invalid_current_password (a new password that is itself invalid is checked first, with 400 bad_request). An administrator can set a new password for a user under Admin → Users → [user] → Reset password, which is shown only for accounts that have a password.

Repeated wrong passwords for one address are throttled: after AUTH_RATE_LIMIT_PER_MINUTE failures in a minute (10 by default), further attempts get 429. Wrong current-password guesses on the change-password route are throttled the same way, per account, against a separate counter; the correct password always works.

When SAML login is enabled

Turning on Enable SAML login removes password sign-in for Staff and User accounts. Administrators keep it as a failsafe: if the identity provider is unavailable, an administrator can still sign in with their password on the normal login page. Enabling OIDC does not remove password sign-in for anyone.

Second factor: authenticator app and passkeys

A password sign-in can be followed by a second factor: a six-digit code from an authenticator app (TOTP, RFC 6238: Google Authenticator, Authy, 1Password, Bitwarden and others), or a passkey or hardware security key. A passkey is used after the password, not instead of it.

Second factors are checked only while Admin → Settings → Authentication → Multi-factor authentication → Enable MFA is on. It is off by default. A sign-in through SAML or OIDC is not asked for a local second factor; that is the identity provider's job.

Enrolling

Each user enrols on their own Your account page:

  • Authenticator app: Set up an authenticator app shows a QR code and a text secret. Scan it, then enter the current six-digit code to confirm.
  • Passkey: name the key and click Add a passkey. The browser or the security key does the rest. A user can hold several passkeys and remove any of them.

Requiring a second factor

Require MFA for roles, shown once MFA is enabled, makes a second factor mandatory for Admin, Staff or User accounts. A user in a required role with no factor is taken through authenticator setup at their next sign-in and cannot continue until it is done. With no role ticked, a second factor is optional.

Signing in

  1. The user enters their email and password.
  2. If they have an authenticator, they are asked for its code. If they have only passkeys, they are asked to confirm with one.
  3. Until the second step succeeds, the session can do nothing but finish signing in.

That half-signed-in session expires: the user has 5 minutes after the password to enter a code or confirm with a passkey, and 15 minutes when they still have to set up their first factor, which takes longer. The clock starts at the password step (for a new self-registered account, when its email address is verified) and nothing restarts it, not even saving a new authenticator secret. Past the deadline the session is deleted and the next request is refused with 401; the user signs in again with their password. A code sent after the deadline is not checked, so it does not use up one of the five attempts.

Five wrong codes in a row lock the account's code entry for 15 minutes.

Losing every factor

There are no recovery codes. A user who has lost their authenticator and every passkey is reset by an administrator: Admin → Users → [user] → Reset MFA clears the authenticator and every passkey and ends the user's sessions. They then sign in with their password and enrol again; if MFA is required for their role, they are asked to at that sign-in.

An administrator with no other administrator to reset them recovers on the server. docker compose exec app /app/server reset-factors <email> clears their authenticator and passkeys. docker compose exec app /app/server unlock <email> does that and more, for an account that is also disabled, locked out of code entry, or without a usable password. See Locked out? and Admin Guide: Users.

After an unlock: choosing a new password

An unlock gives the account a random password, printed once on the server. When the person signs in with it, the login page says they signed in with a password an administrator generated for them and asks them to choose a new one (Choose a new password). Until they do, the session can do nothing else, and the API answers 403 password_change_required on every route except the password change.

Passkeys need a domain name

A passkey is tied to a domain name, so passkeys work only when the host in BASE_URL is a domain name such as help.example.com, or localhost. If BASE_URL is an IP address (http://192.168.1.10:8080), a single-word host (http://helpdesk:8080) or a host with non-ASCII characters, passkeys are turned off. The server still starts, and administrators see a banner, Passkeys are unavailable, explaining why. The passkey routes answer 503 passkeys_unavailable.

  • An account whose only second factor is a passkey cannot sign in while passkeys are off. It is refused with 403 passkey_unavailable and told to ask an administrator to reset its sign-in factors. Reset MFA clears the passkey, and the person then enrols an authenticator app. Accounts with an authenticator app are unaffected.
  • To use passkeys, give the help desk a DNS name and set BASE_URL to it. Passkeys registered under a different domain stop working when the domain changes.

Second factors in the API

For a programmatic sign-in, submit the code to POST /api/v1/auth/local/mfa/verify after a successful password sign-in, or complete a passkey with POST /api/v1/auth/local/passkey/start and /finish. API keys and OAuth clients are refused on these routes. See the API Reference.

SAML 2.0 SSO

Go Help Desk acts as a SAML 2.0 Service Provider (SP) and works with any standards-compliant Identity Provider. It is configured entirely under Admin → Settings → Authentication → SAML. Saving the settings loads the IdP metadata, either by fetching it from a URL or from XML you paste or upload, and applies the change at once, with no restart.

General setup

1

Generate an SP certificate and private key

The SP presents a certificate to the IdP for request signing and response verification.

openssl req -x509 -newkey rsa:4096 \
  -keyout saml.key -out saml.crt \
  -days 3650 -nodes \
  -subj "/CN=Go Help Desk"
2

Register the SP with your IdP

Your SP metadata, which is also the SP entity ID, is at:

<BASE_URL>/api/v1/auth/saml/metadata

The ACS (Assertion Consumer Service) URL is:

<BASE_URL>/api/v1/auth/saml/acs

Configure the IdP to send the user's email address, as an attribute named email (or mail), or as an email-format NameID. With Microsoft Entra ID you do not need to add an email or displayName claim: its default claims are read. The email is read from email, mail, the LDAP mail attribute (urn:oid:0.9.2342.19200300.100.1.3) or Microsoft Entra ID's emailaddress claim, falling back to the NameID. For the display name, Go Help Desk reads displayName (or Entra ID's displayname claim), then cn, then name, then the given name (givenName, firstName or Entra ID's givenname claim) and surname (sn, lastName or Entra ID's surname claim) together, or either alone if only one is sent, then Entra ID's name claim (last, because Entra fills it with the user principal name, not a person's name), and finally the email address. Each sign-in rewrites the stored name from these, so an identity provider that starts sending a name changes the display name at the next sign-in.

3

Enter the settings

Under Admin → Settings → Authentication → SAML, turn on Enable SAML login, then choose how to give the IdP metadata, either URL (IdP metadata URL) or XML (paste it into IdP metadata XML, or use Upload .xml to load a file into the same box). Then fill in SP certificate (PEM) and SP private key (PEM), and save. The two metadata choices are alternatives: a save that would leave both set is refused (saml_metadata_conflict). Pasted XML is checked before anything is saved. It is refused (invalid_saml_metadata) if it is not SAML metadata, has no identity provider section (often this server's own metadata pasted by mistake), or has no signing certificate; and a document over 256 KiB is refused (saml_metadata_too_large). The XML is shown again after saving, and it is never refreshed: when your identity provider changes its signing certificate, paste its new metadata. A URL is fetched again at each save and each restart. A save that would leave no administrator able to sign in is refused.

4

Test with a non-admin account

Open a private browser window and click Sign in with SAML on the login page. Keep your administrator session open until it works; your administrator password still signs you in either way.

IdP-specific setup guides

Okta
  1. In Okta Admin: Applications → Create App Integration → SAML 2.0
  2. On the SAML Settings page:
    • Single sign-on URL: <BASE_URL>/api/v1/auth/saml/acs
    • Audience URI (SP Entity ID): <BASE_URL>/api/v1/auth/saml/metadata
    • Name ID format: EmailAddress
  3. Under Attribute Statements, add:
    • email → user.email
    • givenName → user.firstName
    • sn → user.lastName
  4. Finish the app creation. Go to the Sign On tab and copy the Identity Provider metadata URL.
  5. Paste that URL into IdP metadata URL.
  6. Assign users or groups to the Okta application.
Microsoft Azure AD / Entra ID
  1. In the Azure portal: Microsoft Entra ID → Enterprise applications → New application → Create your own application. Choose Integrate any other application you don't find in the gallery.
  2. Go to Single sign-on → SAML.
  3. Under Basic SAML Configuration:
    • Identifier (Entity ID): <BASE_URL>/api/v1/auth/saml/metadata
    • Reply URL (ACS): <BASE_URL>/api/v1/auth/saml/acs
  4. Under Attributes & Claims, add claims named email (the user's email address) and displayName (their display name), with no namespace.
  5. Under SAML Certificates, copy the App Federation Metadata Url.
  6. Paste that URL into IdP metadata URL.
  7. Under Users and groups, assign the users or groups that should have access.
Google Workspace
  1. In Google Admin console: Apps → Web and mobile apps → Add app → Add custom SAML app.
  2. Give the app a name and click Continue.
  3. On the Google Identity Provider details page, click Download Metadata. You can paste or upload that file as IdP metadata XML, or host it at a stable URL.
  4. Under Service provider details:
    • ACS URL: <BASE_URL>/api/v1/auth/saml/acs
    • Entity ID: <BASE_URL>/api/v1/auth/saml/metadata
    • Name ID format: EMAIL
  5. Under Attribute mapping:
    • Primary Email → email
    • First name → givenName
    • Last name → sn
  6. Paste the downloaded XML into IdP metadata XML (or upload the file), or paste the URL of your hosted copy into IdP metadata URL.
  7. In the app settings, turn on access for the relevant organizational units.

Just-in-time user provisioning

When someone signs in through SAML for the first time, an account is created from the assertion with the User role, provided their email domain is on the Allowed email domains list (an empty list allows any domain; entries and addresses must be ASCII, see Addresses must be ASCII). Promote accounts to Staff or Admin from Admin → Users.

Later sign-ins update the user's email address and name from the IdP, but never their role.

SP certificate rotation

Generate a new certificate and key, add the new certificate to your IdP's configuration (most IdPs accept a secondary certificate during a transition), then upload the new certificate and key under Admin → Settings → Authentication → SAML and save.

Administrator failsafe. Administrators can always sign in with their local password on the login page, even with SAML login enabled. Do not lose your administrator password.

OpenID Connect (OIDC)

OIDC is configured under Admin → Settings → Authentication → OIDC / OpenID Connect: Enable OIDC login, the provider's Issuer URL, a Client ID and a Client secret. The secret is write-only; leaving it blank on a later save keeps the stored one. Register this redirect URL with the provider, which the settings page shows with a copy button:

<BASE_URL>/api/v1/auth/oidc/callback

Saving applies the change without a restart. The login page then offers Sign in with OIDC.

  • Go Help Desk asks for the openid, profile and email scopes, and uses the email address only when the provider marks it verified.
  • The first sign-in creates an account with the User role, subject to Allowed email domains. A sign-in can also attach to an existing account with the same verified address, unless that account is an administrator's or already uses SAML.
  • A save that would leave no administrator able to sign in is refused, here as for SAML.

Guest access

Guest submission is off by default. Turn it on under Admin → Settings → General → Submissions → Guest submission. Up to and including 1.2.0 the pieces existed and did not connect: turning the toggle on produced no error and no guest tickets. It shipped as issue #154.

A guest is not an account. There is no guest password, no guest session and no guest role — possession of a private link is the whole credential, and possession of the mailbox it was sent to is what earns it.

How a guest gets in

  1. They submit a ticket at /submit. The page shows a tracking number and the server emails the address a link to that one ticket.
  2. The link is /g#<token>. The token sits after the # deliberately: a fragment is never sent to the server, so it cannot land in a request log. The page reads it once and removes it from the address bar, so it survives neither browser history nor a screenshot of the URL.
  3. From then on the browser sends it as an Authorization: Guest <token> header to the guest API: read the ticket, reply to it, and open a follow-up once it is closed. A guest can also add files to the ticket from the guest page, but only when an administrator has turned on Guests may attach files (off by default).

What the token is, and how long it lives

PropertyValue
Length32 random bytes, hex encoded
Stored asA SHA-256 hash. The raw value is never written down anywhere on the server.
ScopeExactly one ticket. The token names the ticket; there is no ticket id in any guest URL.
Lifetime30 days from issue, as an outer bound. On an active ticket it is replaced sooner, every time the help desk writes to the guest (next row).
RotatedOn ticket creation, on a staff reply that notifies the customer, on a status change, on resolve, on a reopen by staff, and on a re-request. The old link stops working immediately: there is no grace period, so the newest email is always the one that works.
On closeNot revoked. Closing stops the rotation and sends no mail. The last link still opens the ticket, read-only, until it expires, and can open a follow-up.
Guest submission offSuspended, not revoked. While Guest submission is off, every link answers 404. Switch it back on and the links that have not expired work again.

Every failure on a guest link, a wrong or expired token, a write to a closed ticket or guest submission being switched off, answers an identical 404, so none of them can be told apart from outside.

Re-requesting a lost link

/track takes the tracking number and the email address and mails a fresh link. On an open ticket it replaces the previous one; on a closed ticket it is added beside it, read-only. It always answers the same way, whether or not those details matched a ticket, so it cannot be used to discover which tickets exist. It works for open and closed tickets. One request per ticket every five minutes.

Rate limiting

Guest submission and link re-requests share the sign-in rate limiter: AUTH_RATE_LIMIT_PER_MINUTE a minute (10 by default), keyed on the client address. The shipped docker-compose.yml passes that variable to the app, so under Compose you set it in .env.

Behind a reverse proxy, that key is the proxy. The limiter reads the connection's remote address and deliberately does not trust a forwarded-for header, so every visitor arriving through one proxy shares one bucket. Rate-limit guest endpoints at your proxy if you need a per-visitor limit.

What a guest can and cannot do

  • Can read the ticket's subject, description, status and public replies, and post a reply. Lifecycle rules still apply, including the reopen window.
  • Can open one follow-up from their ticket once it is closed.
  • Cannot see internal notes, staff names, the assignee, the reporter or resolution notes. The guest view is built from a deliberately narrow set of fields rather than by hiding parts of the normal one.
  • Cannot attach a file unless an administrator has turned on Guests may attach files (off by default), and cannot download an attachment. The guest view does not indicate whether a ticket has any.
  • Cannot reach any other ticket. The token names one.

Guest notification email carries no ticket content, only the tracking number and the link. That has been true since v1.2.0.

Turning guest submission on needs a signed-in administrator. Like the MFA, SSO and registration settings, guest_submission_enabled cannot be changed by an API key or OAuth client: they get 403 session_required. A value that is not a boolean is refused.

API keys and OAuth clients

API keys are long-lived credentials for scripts, CI pipelines and tool integrations where a browser sign-in is impractical. OAuth clients do the same job with short-lived tokens. A key is created by a signed-in person; a key cannot create another key or an OAuth client.

Who can have a key

  • Administrators always. Staff only while Staff may create their own API keys is on (Admin → Settings → Authentication → API keys; off by default, and only a signed-in administrator can change it). Turning it off stops new keys only: existing keys keep working, and staff can still list and revoke their own.
  • Requesters never own a key, and neither do service accounts. An administrator can issue a key on behalf of a staff member (or for themselves), never for another administrator.
  • A key acts within its owner's current role. Promoting a staff member who holds an administrator-issued key leaves an administrator holding it; revoke it if that is not wanted.

Creating a key

  1. An administrator goes to Admin → API Keys and uses Create new key, choosing the owner (themselves or a staff member). Staff go to Account → API keys.
  2. Give the key a descriptive name (e.g. monitoring-script), choose its scopes and an expiry date. A key must have at least one scope. Staff keys can carry tickets:read, tickets:write, groups:read and audit:read (users:read is no longer offered: its one staff route, the requester lookup, is session-only).
  3. Every new key must expire, no later than the maximum lifetime: Longest an API key may live, a slider with stops of 1 to 5 years and Never (default 2 years; the settings page shows a red warning above 2). The form offers the longest allowed date by default. Only at Never may the date be left out. Keys made before the upgrade keep working; one with no expiry or one past the current limit is shown as "No expiry (longer than the current limit)" so it can be rotated.
  4. The key is shown exactly once after creation. Copy it into a secret manager or CI secret store. It cannot be retrieved later. A key issued for you by an administrator is marked "Issued for you by an administrator" on your Account page.

Keys are stored as SHA-256 hashes, so a copy of the database does not reveal them. Every key issued or revoked is written to the audit log (api_key_issued, api_key_revoked).

Using a key

Send the key in the Authorization header with the ApiKey scheme:

curl https://helpdesk.example.com/api/v1/tickets \
  -H "Authorization: ApiKey GHD_3f8a…"

The REST API and the MCP server accept API keys, except on the routes that change how an account signs in (password, second factors, passkeys), the routes that create keys or OAuth clients, the routes that write users or group membership, and the settings that need a signed-in administrator. Those refuse every API key and OAuth client.

Permissions

A key acts as its owner, within the owner's role, and only within the scopes it was given. A key's scopes can never exceed its owner's role. Keys can read users and groups but cannot write them, cannot create keys or OAuth clients, and cannot change a few settings that decide who can sign in or who sees tickets (see REST API: API keys). The old users:write scope is no longer offered.

Before 1.3.0 a key acted as the administrator who created it, but only within the scopes it was given. There is no wildcard scope. GET /api/v1/admin/scopes lists them. See REST API: Scopes.

OAuth clients

Under Admin → OAuth Clients, an administrator creates a client with its scopes. The client also gets a service user, named after it. The client exchanges its ID and secret for a short-lived bearer token at POST /api/v1/auth/oauth/token and sends it as Authorization: Bearer <token>. The client acts as its service user, at that user's role: staff by default, or user, never administrator. A client holding tickets:write can create tickets and replies, recorded under the client's name.

  • The service user appears under Admin → Users with a Service badge, and in the client list as (service user). An administrator can rename it (which renames the client), set its role to staff or user, give it groups and disable it. Its email, the administrator role and a second-factor reset are refused (409 service_account). Disabling it stops the client.
  • The user's groups are the client's ticket scope. When staff are limited to their group scope, a client whose user is in no group sees no tickets; the client list says so, and the admin warning banner lists such clients.
  • A service user never signs in: it has no password, second factor, passkey or SSO identity, and cannot be made an administrator. It is never emailed.
  • Deleting the client deletes its service user. The tickets and replies it wrote keep its name.

Revoking a key

An administrator clicks Revoke next to the key on Admin → API Keys, and staff revoke their own under Account → API keys. Revocation is immediate: the next request with that key gets 401. Disabling or deleting the key's owner also stops the key working. An administrator who resets someone's password can tick Also revoke this person's API keys to delete every key they own; a person changing their own password, Forgot password, unlock and reset-factors never touch keys.

A webhook that a key created, or last changed the URL of, is paused when the key is revoked or expires (see the admin guide).

Key naming conventions

Since the key value cannot be retrieved after creation, the name is your only way to identify a key later. Use names that describe the consumer: pagerduty-webhook, ci-pipeline-prod, alex-cli-dev. Include dates in names if you rotate keys on a schedule.
