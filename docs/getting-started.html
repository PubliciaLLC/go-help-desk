Getting Started

Deploy Go Help Desk with Docker Compose in under five minutes.

Go Help Desk is distributed as a single Go binary with the React frontend embedded — there is nothing to install or serve beyond the binary and a PostgreSQL database. The Docker Compose stack in docker/ sets both up with a single command.

New in 1.3.0.

  • Published images for amd64 and arm64. docker compose up -d pulls them. Building from source is still supported.
  • Virus scanning is opt-in in Docker Compose. See Virus scanning.
  • Setup also asks for the first category, so a new instance can file a ticket.
  • Example secrets are reported as insecure at startup and in an administrator's warning banner.
  • Email is queued and retried. Webhooks are sent once and are not retried.
  • MFA_ENABLED and GUEST_SUBMISSION_ENABLED are removed. Nothing read them.

Upgrading from 1.2? Read the upgrade notes.

Architecture overview

  • Binary: a single Go executable that serves the REST API at /api/, the MCP server at /mcp/, and the React SPA at /.
  • Frontend: compiled at build time and embedded in the binary via go:embed. No Node.js in production.
  • Database: PostgreSQL. Schema migrations run automatically on every startup before accepting traffic.
  • Plugins: a plugin system is planned for v2. Plugins cannot be installed in 1.3.0.
  • Image: published to ghcr.io/publiciallc/go-help-desk for amd64 and arm64.

Quick start

Requirements: Docker Engine 24+ and Docker Compose V2.

1

Get the Compose file

git clone https://github.com/PubliciaLLC/go-help-desk
cd go-help-desk/docker
2

Create your environment file

cp .env.example .env

Open .env and set SESSION_SECRET and JWT_SECRET. Set BASE_URL as well if you will not reach the instance at http://localhost:8080. Generate secure secrets with openssl rand -base64 32.

BASE_URL=http://localhost:8080
SESSION_SECRET=<at-least-32-random-chars>
JWT_SECRET=<different-32-random-chars>

Compose refuses to start until SESSION_SECRET and JWT_SECRET are set. The example values in .env.example let the server start, but it reports them as insecure at startup and in an administrator's warning banner until you replace them.

3

Start the stack

docker compose up -d

This pulls a published image. Nothing is compiled on your machine, and one image name covers both Intel and ARM, including Apple Silicon, because the Docker client picks the right architecture for you. Docker also starts PostgreSQL. Migrations run automatically before the app begins serving traffic. Wait until the health check answers:

curl http://localhost:8080/health
# → {"status":"ok"}
4

Open the app and complete setup

Navigate to http://localhost:8080. On a fresh database the app redirects to /setup, where you enter a name, email address, and password to create the first admin account, and the name of the first category. The setup page is permanently disabled once any user exists, and it cannot be reached again.

Data persistence. Postgres data is stored in docker/data/postgres/ and file attachments in docker/data/attachments/. When virus scanning is enabled, the ClamAV signature database is stored in docker/data/clamav/. These directories are gitignored and survive container restarts and rebuilds.

Verify the installation

curl http://localhost:8080/health
# → {"status":"ok"}

Virus scanning (optional)

Virus scanning is off by default. To turn it on, uncomment these two lines in docker/.env, which you copied from .env.example:

CLAMAV_ADDR=tcp://clamav:3310
COMPOSE_PROFILES=antivirus

The second line starts a ClamAV container, which downloads its signature database (about 300 MB) on first start. Until that finishes the scanner is unreachable, and once an address is set, uploads are refused with 503 while it is unreachable. The clamav/clamav image is published for amd64 only, so on Apple Silicon it runs under emulation. See Virus scanning (ClamAV) for the settings.

Building from source

Building the image yourself is fully supported and is not a fallback. Some people self-host precisely so that they can run what they built rather than an image somebody else produced. From the docker directory:

docker compose -f docker-compose.yml -f docker-compose.build.yml up -d --build

This path requires Docker Buildx. It cross-compiles for your host's real architecture rather than emulating it, and that needs the docker buildx CLI plugin. Without it, Compose falls back to the classic builder, which does not set $BUILDPLATFORM, and the Dockerfile then has no correct platform to build for (see #297 and #301). Docker Desktop ships Buildx. Colima and some Linux installations do not. If docker buildx version fails, install it. On macOS with Homebrew, including Colima:

brew install docker-buildx
mkdir -p ~/.docker/cli-plugins
ln -sfn "$(brew --prefix)/opt/docker-buildx/bin/docker-buildx" ~/.docker/cli-plugins/docker-buildx

See docs.docker.com/build/architecture for other platforms.

Pinning a version

docker compose up -d runs the version pinned in docker-compose.yml. To run a different one, set GHD_VERSION in docker/.env:

GHD_VERSION=1.3.0

Released versions are published as 1.3.0 and 1.3, and the newest stable release is also latest. A prerelease is published under its exact name only, such as 1.4.0-beta, and never moves latest, so following latest will not put you on a beta. Images live at ghcr.io/publiciallc/go-help-desk.

Do not run edge. It is rebuilt on every push to the release branch and overwritten in place, so two machines pulling it on the same day can be running different code.

Configuration reference

Configuration is read from environment variables at startup. Variables marked required cause the server to exit with an error if unset or empty.

  • Environment variables control infrastructure. Feature switches (SAML, OIDC, MFA, SLA, guest submission, signup) and branding are managed under Admin → Settings and stored in the database.
  • Changing an auth-related setting requires a signed-in administrator. An API key cannot, whatever scopes it holds.
  • Variables are read once, at startup. After you change .env, run docker compose up -d again.

Required

VariableDefaultDescription
DATABASE_URLrequiredPostgreSQL connection string, for example postgres://user:pass@host:5432/db?sslmode=disable. Migrations run against this database at every start, before the server accepts traffic.
BASE_URLrequiredPublic URL of the instance, for example https://helpdesk.example.com. Write it without a trailing slash; some uses (the OIDC redirect, SAML and passkeys) take it as written. Used in email and guest links, in the SAML and passkey settings, and as the default OIDC redirect ({BASE_URL}/api/v1/auth/oidc/callback).
SESSION_SECRETrequiredAt least 32 characters, or the server refuses to start. Signs and encrypts session cookies. Changing it signs everyone out. Generate one with openssl rand -base64 32.
JWT_SECRETrequiredSigns the OAuth2 access tokens and is checked on API bearer tokens. No minimum length is enforced, but use 32 or more characters.

Example secrets are insecure. The example values in docker/.env.example let the server start, but anyone who knows them can forge sessions and API tokens. The server logs an error at startup, and administrators see a warning banner, when SESSION_SECRET or JWT_SECRET is an example value or contains change-me, changeme, insecure, example or placeholder.

Server

VariableDefaultDescription
HTTP_PORT8080TCP port the HTTP server listens on. The shipped Compose file fixes it at 8080. Change it when running a bare-metal install behind a reverse proxy that handles TLS.
ATTACHMENT_DIR/data/attachmentsFilesystem path where uploaded files and the uploaded logo are stored. Created on first use if it does not exist. Must be writable by the application user, which is ghd (uid 100) in the image. The shipped Compose file does not pass this variable through.
LOG_LEVELinfodebug, info, warn or error. An unrecognised value is logged as a warning and info is used. Logs are JSON, written to stdout.
AUTH_RATE_LIMIT_PER_MINUTE10Failed password attempts allowed per account (keyed on the email address) per minute before the server answers 429. Signup attempts from one source address are limited by the same number. 0 disables both limits. Counters are kept in memory, so a restart clears them and each replica keeps its own. TOTP verification has its own budget, which is not configurable. The shipped Compose file does not pass this variable through.

Email (SMTP)

Email is sent only when both SMTP_HOST and SMTP_FROM are set. Without email, self-service signup cannot complete, and guests receive no link. These variables are read at startup, so restart the server after changing them.

Mail is queued in a database outbox and sent by a background worker. A failed send is retried after 30 seconds, with the wait doubling each time, for eight attempts over about an hour. Webhooks are not retried: each one is sent once.

VariableDefaultDescription
SMTP_HOST—Hostname of the SMTP server, for example smtp.sendgrid.net or email-smtp.us-east-1.amazonaws.com.
SMTP_PORT587SMTP port. The connection is upgraded with STARTTLS when the server offers it. There is no implicit TLS (SMTPS) mode, so port 465 will not work.
SMTP_USER—Username for SMTP login. Login is attempted when this is set and the server offers AUTH.
SMTP_PASSWORD—Password for SMTP login. Use a secret manager or Docker secret in production, not a plain .env file.
SMTP_FROM—The From address for all outgoing email, for example helpdesk@example.com. A display name is allowed: Help Desk <helpdesk@example.com>.

Virus scanning (ClamAV)

VariableDefaultDescription
CLAMAV_ADDRunsetAddress of a ClamAV daemon: tcp://host:3310 or unix:///path/to/clamd.sock. When unset, attachments are not scanned. In Docker Compose, set it in .env together with COMPOSE_PROFILES=antivirus; see Virus scanning under Quick start. An administrator can change the address under Admin → Settings → Attachments → Malware scanning without a restart.

Once an address is set, the scan policy defaults to required: an upload is refused with 503 and a Retry-After header while the scanner cannot be reached. Administrators can change the policy under Admin → Settings → Attachments → Malware scanning. See Admin Guide: Attachments.

Feature switches

VariableDefaultDescription
SLA_ENABLEDfalseTurns SLA tracking on at every start. It never turns it off. The switch is under Admin → Settings, in the SLA section, so this variable only lets an instance start with SLA tracking on.

Feature switches are set under Admin → Settings and stored in the database. Multi-factor authentication, guest submission (see Guest ticket submission) and signup are switched there too. No environment variable controls SAML or OIDC. Configure them under Admin → Settings, in the SAML and OIDC sections. See Authentication: SAML 2.0.

The variables MFA_ENABLED and GUEST_SUBMISSION_ENABLED were removed in 1.3.0 because nothing read them. Setting them has no effect.

With Docker Compose

.env values reach the app only through the environment block of the app service in docker-compose.yml. The shipped file passes through BASE_URL (default http://localhost:8080), SESSION_SECRET, JWT_SECRET, CLAMAV_ADDR, SMTP_HOST, SMTP_PORT, SMTP_USER, SMTP_PASSWORD, SMTP_FROM, SLA_ENABLED and LOG_LEVEL. DATABASE_URL and HTTP_PORT are fixed in the file.

Any other variable set in .env has no effect, for example AUTH_RATE_LIMIT_PER_MINUTE or ATTACHMENT_DIR. To use one, add it in docker/docker-compose.override.yml, which Compose reads automatically and git pull does not touch:

services:
  app:
    environment:
      AUTH_RATE_LIMIT_PER_MINUTE: "5"

When you build from source, add -f docker-compose.override.yml to the build command, because Compose skips the override file when -f is given.

GHD_VERSION is read by Compose, not by the app; see Pinning a version. COMPOSE_PROFILES=antivirus starts ClamAV.

First-run setup

After completing the /setup wizard and creating your admin account, work through this checklist before inviting users:

  1. Create your CTI hierarchy. Setup has already created the first Category. Go to Admin → Categories and add the rest. See the Admin Guide: Categories for a worked example.
  2. Review ticket statuses. The system creates five default statuses (New, In Progress, Pending, Resolved, Closed). Closed is terminal by default. If you need intermediate statuses (e.g. "Awaiting Vendor"), add them now under Admin → Statuses. See Admin Guide: Statuses and Reopening closed tickets.
  3. Create groups and assign scope. Define which staff teams handle which categories. See Admin Guide: Groups & scope.
  4. Create or invite staff accounts. Create staff accounts from Admin → Users, or have staff register themselves and then promote their role. See Admin Guide: Users & roles.
  5. Configure email (optional). Set SMTP_HOST and SMTP_FROM (both are needed) and any other SMTP variables, then restart. See Email (SMTP).
  6. Configure SLA policies (optional). Turn on SLA tracking under Admin → Settings, then set response and resolution targets per priority or category in the SLA section. See Admin Guide: SLA policies.
  7. Set up SSO (optional). Configure SAML or OIDC under Admin → Settings, in the SAML and OIDC sections. OIDC is reloaded without a restart. See Authentication: SAML 2.0.
  8. Check the warning banner. Administrators see a red banner while an example secret is in use. Replace the secret and restart before inviting users.
  9. Decide audit retention. Choose whether the audit log is kept forever (the default) or pruned, and whether staff can see ticket change history. Both are under Admin → Settings, in the Audit log section. See Admin Guide: Audit log.

Upgrading

cd go-help-desk
git pull
cd docker
docker compose pull
docker compose up -d

If you build from source, do not run the two docker compose commands above. Run the build command from Building from source instead.

Upgrading from 1.2.x? Read Upgrading to 1.3.0 first. Compose installs that scan attachments with the bundled ClamAV must add two lines to .env. See ClamAV is opt-in.

The application runs database migrations automatically on startup, before it begins accepting traffic. There is no manual migration step. If a migration fails (e.g. due to a conflict with manual schema changes), the server exits with an error message — check the container logs.

Back up your database before upgrading in production. Migrations are forward-only; there is no automatic rollback if you need to downgrade.

Zero-downtime upgrades

For production deployments where downtime is unacceptable, the recommended approach is:

  1. Take a database backup.
  2. Pull the new image.
  3. Start a second container with the new image pointing to the same database. Migrations run and complete.
  4. Shift traffic to the new container.
  5. Stop the old container.

This works because migrations are idempotent — running them on an already-migrated database is a no-op.

Kubernetes

A Kubernetes deployment guide and sample manifests are planned for v4. For now, Docker Compose is the supported deployment method.
